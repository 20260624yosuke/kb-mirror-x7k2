# Eグル×Wiki×メタデータ パーソナライズ構想の再設計

2026-07-03、武田さんから「成果物が浅い。構想は有効だが実用設計に引き戻せ」という要求を受けた
再設計の正本。慰め・撤退案ではなく、(1)実現性評価 (2)接続設計 (3)失敗原因の分解
(4)取捨と検証順 (5)実物への落とし込み、を扱う。

## 出発点の仮説(維持する)

Eagleの画像ベクトル + Wiki内メタデータ + Eagle側メタデータを接続すれば、単なるフォルダ整理でなく
**創作ワークフロー全体に還元されるパーソナライズされたメタデータ運用**が作れる — この仮説自体は有効。

## 1. 実現性評価(材料の査定)

- **Eagle 384次元ベクトル: 弱い(source-backed)**。フォルダ復元 top1 44%(100件測定)、
  dry-run 20枚は武田さん目視で全滅。モデル非公開・文字で引けない・資料種別(フィギュア写真/
  イラスト/スクショ)を区別できない。用途は「粗い候補出し」まで。**この部品は自前CLIP系に交換
  可能で、交換しても仮説は無傷**。
- **Eagle側メタデータ: 最強・未活用**。①フォルダ体系570個=武田さんが命名した個人辞書
  (軸構造: 01配色/02絵柄/03人体/04エスキース・構図・季節/05服装・小物/06明暗・質感/07作品・キャラ)
  ②保存時注釈【LLM用】(author_id/post_id/captured_at) ③保存時の1フォルダ判子=意図の一次情報
  ④14,265枚の複数フォルダ手作業分け(ノイズ混じりの教師)。
- **Wiki内メタデータ: 本物だが薄い**。Canvas使用実績のEagle確定リンクは184枚=0.5%
  (学習材料には不足、**答え合わせ用**が現実的)。Coloso概念群は「なぜ良い参考か」ラベルの語彙
  として将来接続(還元先)。
- **成立ライン**: 言葉で自分のライブラリを引く / 資料種別の区別 / 軸別のフォルダ候補+3値仕分け /
  Canvasテーマに合う資料シート生成。**不成立**: ピクセルからの意図読み取り、完全自動の全量
  振り分け、Eagle 384を頭脳にすること。

## 2. 接続設計

### データ層(facts.db に追加)

```
① vectors_clip   : 自前CLIP/SigLIPベクトル。34k枚×1回計算(M2ローカル・数時間・無料)。
                   出どころラベル付き(eagle-384と併存)。モデル・環境は外付けSSD内。
② content_type   : 資料種別(イラスト/フィギュア写真/実写人物/実写物・風景/文字スクショ/マンガ)。
                   CLIPゼロショットで判定。2026-07-03の全滅の主因はこの層の欠如。
③ folder_ontology: フォルダ辞書(570個→意味1行+検索用言い換え)。フォルダ名から自動生成し
                   中身サンプルで検証。正本はJSON、人間可読版をwikiへ。
```

### 判定エンジン(v1の構造欠陥の修正)

- **軸ごとに独立して候補を出す**(v1は570フォルダを1つの多数決に混ぜた)。
- スコア = 意味一致(画像↔フォルダ辞書文) + 近傍投票(手作業14k、フォルダ規模の偏り補正) +
  規則(ファイル名 x-作者-→02_絵柄、注釈author_id→07_作品/キャラ)。
- 最初に資料種別ゲート。フィギュア写真をイラスト軸に流さない。実写コスプレ→05_コスプレ+作品軸。
  スクショ→how-to系か保留。
- 出力は3値(自動/画像確認/保留)+画像カードHTML(提示形式として機能実証済み)。

### 創作への還元(Obsidianに落ちる形)

- `sheet` コマンド: Canvasファイルまたはテーマ文 → 意図に合う資料20〜40枚を根拠付きで
  資料シート化(HTML、またはCanvasファイル直接生成=画像ノード+根拠テキストノード。
  canvas-reference-tools の運用に乗る)。
- Canvas sidecar used-for は「過去に実際使った画像をシートが上位に出せるか」の答え合わせ。
- 将来層: Coloso概念ラベル(「逆光の対比の参考」等)、月次保存傾向スナップショット。
- Eagle書き戻しは確定分のみMCP(バッチ・全操作ログ・取り消し可)。正本はfacts.db、Eagleは投影。

## 3. 浅くなった原因の分解

- **プロジェクト設計(最大)**: 「創作に還元されるメタデータ運用」が「2万枚のフォルダ整理」へ
  手段の目的化。成果物の定義を振り分け精度に置いたため、精度が出ない=何も残らない構造。
- **情報整理**: 対象プールを50枚眺める基本動作を着手前に誰もやらなかった(未整理プールの大半が
  フィギュア写真・実写・スクショと最終日に判明)。フォルダ辞書を作らず多数決に使用。
  材料の下調べの欠落。
- **指示設計・運用**: Codexが数値表をユーザー向けに提出(役割取り違え)。Fableもしきい値を
  実データ確認前に設定(初回全hold)、Firefoxのローカルファイル規則未検証(画像ゼロHTML)、
  開き方の説明省略。小さなミスの積み重ねが「トークン消費の割に浅い」体験を構成。
- **モデル性能**: Eagle 384の弱さは事実。ただしFableの直接視認(v2)は実用水準に近く、
  限界は「目」でなく**向ける先と順番の設計**。上位モデルの視認を全量に使うのはコスト破綻
  →「ローカルCLIPで候補・種別、迷い分だけ上位モデルの目」の配分が正解。

## 追記(2026-07-04 ブレスト整理での訂正・新事実)

### 優先順位の訂正(user-stated を受けて)

武田さんの実際の痛点は「探す対象が具体的なとき(制服・ローアングル・シュシュ)に、探しに行ったら
そこにある状態」= **検索・再分類が主役**。資料シート(Canvas生成)は「既に創作段階に入った場面」の
応用であり後回し。前版で段階4(シート)を本体と置いたのはズレ → 検索を本体に再配置。

### 実測(source-backed 2026-07-04): Eagle標準の文字検索では解けない

Eagle AI Search プラグイン(ready・34,922件同期済み・text128次元/image384次元)を実際に
`制服 セーラー服 学生服` と `ローアングル あおり構図 下から見上げる` で叩いた。
結果は**全件が「既に該当名のフォルダに入っている画像」**(制服→全hit が 05_服装_制服jk_01 所属、
ローアングル→全hit が 04_構図_ローアングル_02/06 等所属)。つまりEagleの文字検索はフォルダ名・
タグ・ファイル名(テキスト埋め込み)を見ており、**画像の中身は見ていない**。
「フォルダに入れていない物は見つからない」問題はEagle標準機能では原理的に解けないと確定。
→ 内容の言語化層(自前CLIP)の必要性が実測で裏付けられた。

### 新事実(user-stated): 保存ワークフローの歴史と教師汚染の具体源

- 以前はEagle公式拡張で未整理へ大量保存 → 未整理6,000枚で処理不能に → 以後「保存時に1フォルダ
  だけ判子」の習慣へ。ここ半年の保存分は実質、厳密なフォルダ分けがされていない。
- 過去にEagle配布のskillでLLM整理を実行したが精度に満足できず**結果を放置**。
  「画像にいらないフォルダ分けがされてる」= 現在の複数フォルダ所属には
  **手作業分け(信頼できる教師)とLLMジャンク(汚染)が混在**。
- **実測(2026-07-04、34,922枚全スキャン)**: ai_タグ付き5,187枚の意味あるフォルダ数は
  平均4.42(なし29,735枚は平均2.47)。フォルダ3つ以上の帯14,255枚のうち**ai_タグ付きが
  4,092枚=29%**。ai_タグ付きの更新月は2025-01〜03(約2,700枚)と2026-02〜03(約1,100枚)の
  2時期に集中。→ 教師の第一候補は「3+フォルダ かつ ai_タグなし」の**10,163枚**とし、
  ai_付き4,092枚は教師から除外(安全側。検索索引の対象としては残す)。
  未確認: ai_なし10,163枚が全て手作業か(スポット目視で検証可)/ai_付きに手作業分けが
  混在する可能性/2時期のどちらがEagle配布skill実行か。
- 保存時に全振り分けさせる方向は不採用(保存が億劫になる=成長ループが止まる)。
  **保存は軽いまま、保存後にLLM+メタデータで補完**が設計の前提。

### 出口の追加候補: タグ書き戻し+スマートフォルダ

物理フォルダ移動より軽い materialize として、内容ラベルをEagleタグ(新接頭辞・ai_とは分離)で
書き戻し、Eagleのスマートフォルダ(条件フォルダ)で「制服系すべて」が自動で集まる棚を作る案。
非破壊・一括取り消し可能・2万枚規模でも現実的。精度確認後に100枚パイロットから。

- 実測(2026-07-04): ライブラリ metadata.json に `smartFolders` キーが実在(現在0件=未使用)。
  機能自体はEagleの標準機能(一般知識・2次情報)。実際のUI挙動(タグ条件での自動集約の見え方)は
  100枚パイロットで武田さんの実機確認が必要。
- タグ書き込みの実現性はHTTP API `item/update` で確認済み(2026-07-01実証。foldersは無視されるが
  tags/annotationは効く)。MCPにも `item_add_tags` / `item_remove_tags` あり。タグは各画像の
  metadata.json の `tags` 配列に保存され、削除・一括取り消しが可能(付与ログを残す)。

## 追記(2026-07-04 パイロット判定・全量索引着手・アンサンブル実験)

### 武田さんの判定(目視・ざっくり)

- 水着: 使える / 制服: 使える → 実装(全量索引+検索UI+タグ書き戻し)へ進める判断
- ローアングル: 使えない / 横顔: 使えない / シュシュ: 使えない → 補強策の検討へ

### 実測(2026-07-04): 言い換え文アンサンブルは効果なし(重要な否定結果)

弱い3語の改善案として、複数の英語言い換え文の埋め込みを平均する「アンサンブル検索」を
1,918枚パイロットで試した(`eagle_clip_search.py ensemble` 新設)。結果:
- ローアングル: 単一文 上位20枚中ヒット2 → 4文アンサンブル ヒット2(**変化なし**)
- シュシュ: 単一文 ヒット7 → 4文アンサンブル ヒット7(**変化なし**)
- 横顔: **対応するEagleフォルダが存在せず、対照群による自動採点が不可能**(実測。
  `folders`に横顔/プロフィール系の名前は0件)。武田さんの「使えない」判定は目視のみに基づく。

**判断**: 少なくともこのパイロット規模・このモデルでは、言い換え文の工夫だけでは弱いカテゴリは
改善しない。ボトルネックは文面でなく、SigLIPの画像全体を1本のベクトルに圧縮する方式そのものが
「構図(カメラの向き)」や「画面の一部を占める小物」を弱くしか捉えていないという構造的な限界の
可能性が高い(仮説、未検証)。→ 補強は言い換えでなく**別の技術(タイル分割・vision LLMによる
絞り込み後の目視)**に軸足を移す。

### 生成AIフォルダの除外(2026-07-04 武田さん指示)

「生成ai」を含むフォルダ(全て小文字表記で統一。実測: facts.db全フォルダ名確認済み)に
所属する画像は、検索結果・タグ候補から一律除外する方針を追加。DB再構築は不要で、
候補選定時にフォルダ名でフィルタするだけで足りる(ベクトル自体は生成画像でも変わらず有効な
ため)。`eagle_clip_search.py` の `search`/`tag-review` 双方に適用(`is_generative_ai_polluted`
関数、新設)。

- ライブラリ全体で生成AIフォルダ所属は**4,512枚**。
- 除外の効果(実測): 水着の新規候補は4,037→**2,126枚**、制服は2,158→**973枚**に減少。
- 検証: 制服候補の除外前1位(M6U1I1MBECOT8)は実際に `02_絵柄_MX2J_生成ai_22` 所属と確認、
  除外後1位(MPKURZV5BZKPS)はセーラー服イラストで妥当と目視確認。フィルタが正しく機能。

### タイル分割実験(シュシュ・2026-07-04・結論: 不明瞭)

小物(シュシュ)がCLIPで拾いにくい原因の仮説「画像全体を1本のベクトルに圧縮する過程で
小さい物が薄まる」を検証するため、1,918枚パイロットで画像を5分割(全体+左上/右上/左下/右下)
してそれぞれCLIPにかけ、最大値をその画像のスコアとする方式を試した(一時スクリプトで実施、
既存 `clip_pilot.db` を使い回し、追加ダウンロードなし)。

- 対照群ヒット数(上位20枚): 全体1枚のみ=7 → タイル分割5枚=6(**数値上は横ばい〜微減**)
- ただし上位20枚の中身は大きく違う(一致は20枚中6枚のみ)。タイル分割だけが拾った候補を
  目視すると、**手首に青い布製シュシュが明確に写っている画像**(`MQOYIRPL1OHSA`)を含む、
  対照群フォルダには入っていないが内容的に妥当な当たりを含んでいた。
- **判断**: この規模(1,918枚・対照群100枚)の実験では「タイル分割が明確に効く」とは言えないが、
  「効かない」とも言い切れない。対照群フォルダに入っている画像がシュシュの全量ではない
  (フォルダ未所属の真の当たりがある)ため、この評価方法自体の感度が低い可能性がある。
  結論は保留。全量規模で試すかは費用対効果次第(未着手)。

### 新事実: スマートフォルダ作成はMCPで自動化できない

Eagle MCPの `folder_create` / `folder_update` は通常フォルダ専用で、スマートフォルダ(条件保存)を
作るパラメータが無い(実測: スキーマ確認)。スマートフォルダの作成自体は**武田さんがEagle画面で
手動**(サイドバー右クリック→新規スマートフォルダ→タグ条件を設定)で行う必要がある。
タグの書き戻しまでは自動化できるが、「棚として見える化」の最後の一手は自動化対象外。

## 2026-07-06 プロジェクト断念

武田さん判定:「あまりにも成果物がダメだったから、このプロジェクトも断念だな」。
本プロジェクト(Eagle CLIP/メタデータによるパーソナライズ運用)は断念。

### 経緯

- 服装カテゴリ(水着・制服・メイド服等)の100枚棚は実装・実機確認まで完了し、
  武田さんも一度は承認・実機確認していた
- 次段階(出自軸エンジン・弱カテゴリ補強)で、技術的な検証(辞書の的中率・収量・抜き取り精度)
  はすべてゲートを通過したが、**成果物が武田さんの「見て感じる」実用基準を満たさなかった**。
  絵柄棚(M3)=技術的に的中したが「作者はファイル名・既存フォルダで探せる」ため運用価値薄で
  見送り。弱カテゴリ補強(W1・ローアングル)=収量・精度ゲートとも合格したが、定義した
  「ローアングル」が武田さんの実際に欲しかった資料像とズレていた

### 根本原因(断念前の分析)

このパイプラインには「機械が仕様書どおり動いたか」を確認するゲートはあったが、
**「仕様書が武田さんの欲しいものを表現できているか」を確認する工程が無かった**。
結果、名前と実物の意味が誰にとってもほぼ1対1のカテゴリ(水着・制服等)は成功し、
意味にズレの余地があるカテゴリ(ローアングル・絵柄棚の使い道等)は、全工程が正しく
動いた上で使えない成果物が出た。武田さんは、この構造ごと使いものにならないと判断した。

- Eagle側に残っているもの(取り消しはスコープ外・現状維持): `clip候補_*` タグ群
  (服装カテゴリ、実機確認済みで武田さんが一度は承認したもの)、`実戦_使用済み`
  タグ(Canvas還元で50枚)

  キャラ展開(M4、未着手)
