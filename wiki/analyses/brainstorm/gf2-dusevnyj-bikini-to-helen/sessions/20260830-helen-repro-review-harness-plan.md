## 結論

| 計画 | 答える問い | 変えないもの |
|---|---|---|
| 既存の原作再現計画 | 何を調査し、何を Blender へ実装するか | S6・S8・G10、原作比較、成果物の目標 |
| 新しい実行保証計画 | どんな証拠が揃えば、LLM が次へ進み、完了と言ってよいか | 既存計画の技術内容 |

新計画は、追加調査を増やすための計画ではない。古い状態、証拠の無い否定、検出力のない試験、長い引き継ぎ文から生じる誤答を、次工程へ入る前に機械的に止めるための計画である。

## 既存ハーネスの棚卸し

既存の仕組みは捨てない。次を土台として使う。

- `f46`: 画像比較環境の鮮度
- `f47`: 入力の取得可能性
- `f48`: 主張と根拠の参照
- `f49`: 質問・停止チケット
- `f50`: 事実監査
- `f72`: 否定主張のゲート
- `f97`: 圧縮・実行時入力を含むローカル優先の再照合
- `f128`: 成果物の構造品質
- `f152`: 原作との差を測る視覚ROI
- `quality-gate.json`: plan / batch / complete の段階ゲート

不足しているのはゲートの本数ではない。**ゲート同士を1つの状態遷移へ束ねる契約、検出力の実証、ユーザー指摘を次回の停止条件へ変える台帳**である。

## 提案する3層ハーネス

### 層1: 状態・段階の契約

- 現行状態の正本を1か所にする。
- 各段階は入力SHA、実行器SHA、出力SHA、開始条件、完了条件、停止理由を持つ。
- `done` 1語を禁止し、`process_finished`、`result_verified`、`artifact_verified`、`user_accepted` を分離する。
- 手渡し資料、正本状態、実ファイルが食い違えば次段階を止める。

### 層2: 根拠・因果の契約

- S6・S8・G10ごとに「原作差 → 候補コード → 反証試験 → Blenderで予想される変化」を1本につなぐ。
- 候補が見つかっただけでは Blender を変更しない。
- 陽性対照と陰性対照を持つ。既知の欠陥を入れた変異版で落ちることを確認する。
- 可能な数値は別実装で再計算し、同じ検査器の自己申告を根拠にしない。
- 機械が測らない見た目を、合格と呼ばない。

### 層3: 指摘・報告の契約

- 水着計画の `review-findings.json` と A10 を原作再現側にも適用する。
- 指摘は原文、再発条件、機械判定の可否、変換先、状態を記録する。
- `open` の指摘が1件でもあれば `complete` を止める。
- 人間へは、変化した点、残る差、次の判断1件だけを短く出す。詳細ログは必要時に開ける形にする。

## レビューの分業

### A. 決定的監査（同じ入力なら同じ答え）

- SHA、時刻、入力一覧、状態遷移、正本と手渡し資料の一致
- 未回収数と探索分母の有無
- 旧結果と現行スクリプトの版ずれ
- 変異試験でゲートが実際に落ちるか
- 原本非破壊、出力先、Blend SHA、原作フレーム来歴

### B. 狭いLLM監査

LLMへ広い「レビュー」を依頼しない。S6・S8・G10の各1件について、固定形式で次だけを判定させる。

1. 候補コードが原作差へ因果的につながる説明があるか
2. 説明を否定できる試験があるか
3. 足りない入力が隠されていないか
4. 現行状態と報告に矛盾がないか

出力は `pass / fail / blocked`、根拠参照、未確認点だけに固定する。

### C. 人間判断

- 原作との差として何を許容するか
- 近似版へ切り替えるか
- 代表1〜4件の差が用途上許容できるか

全ファイル監査、失敗原因の診断、数値の再計算を武田さんへ戻さない。

## 別計画の段階案

### H0 現在地の凍結

Blendを変えず、現行Blend SHA、S6/S8/G10、`f166` 結果、run-state、各ゲートの版を1枚に固定する。食い違いは修正せず、まず列挙する。

### H1 既存ゲートの検出力監査

各ゲートについて、測るもの、測らないもの、既知欠陥、変異試験を整理する。壊しても通るゲートは、完了根拠から外す。

### H2 欠陥契約を3件作る

S6、S8、G10ごとに、正解資料、現在値、合格線、入力、候補、反証、停止条件、機械が判定できない点を固定する。

**2026-08-30 選択肢2で決定:** S6だけを先行させず、下の3契約を同じ共通書式で設計し終えてから通し試験を選ぶ。

## 3欠陥の共通契約

3件は、原因も不足入力も違う。ただし、LLMが進んでよい条件は同じ書式に固定する。

| 欄 | 必須内容 | この欄が無いと止めること |
|---|---|---|
| `source_truth` | 原作フレーム、ROI、実行条件、SHA | 原作一致の主張 |
| `current_observation` | 現行Blend SHA、測定値、検査器SHA | 改善・悪化の主張 |
| `coverage` | 探索分母、回収数、未回収数、入力一覧 | 「候補なし」「探索終了」の主張 |
| `causal_bridge` | 原作差、候補コード、入力、予想される画素・形状変化 | Blend変更 |
| `falsifier` | 仮説を否定できる試験と期待結果 | 候補採用 |
| `mutation_tests` | 既知の壊した入力、期待する失敗 | ゲートを完成根拠に使うこと |
| `non_goals` | 機械が測らない見た目・意味 | 用途合格への読み替え |
| `state` | 段階、block理由、根拠参照 | 次段階への遷移 |

共通状態は次の順だけを許す。

`scoped` → `coverage_verified` → `candidate_traced` → `causal_tested` →
`artifact_candidate` → `artifact_measured` → `human_review` → `accepted`

途中で入力が欠ければ `blocked`、根拠が衝突すれば `contested`、反証された候補は `rejected`。
`done` 1語は使わない。別の欠陥が合格しても、残り2件の状態を進めない。

## 契約 S6 — 顔の白飛び

### 正解と現在値

- 正解資料: 原作 `h0157_32` と同構図の frame206、顔ROI。
- 現行Blend SHA: `04ef8b79b3fa5b64…`。
- 現在値: 原作0%、当方39.334%。合格線は白飛び率1%以下。
- 現在の段階: `scoped`。測定門はあるが、原因コードとの因果接続が無い。

### 既に否定された説明

- ACES RRT/ODTの欠落だけが原因という説明。完全転写候補でも39.325%で、ほぼ変化しなかった。
- 全体を暗くすれば解決という説明。`k=0.4`では顔0.194%で門を通るが、全身meanが64.1、原作101.5より37.4暗い。

### 因果接続に必要な証拠

- `InternalLut`、`_Lut_Params`、`_FilmWhiteClip`、露出、bloomを含む実際の処理順。
- 候補コードのbundle、Shader/pass/stage、本文SHA、入力パラメータの来歴。
- 顔だけでなく全身の輝度分布をどう変えるかという予測。
- `f166` 最終修正版の再走査・整合確認後の探索分母。初回7,424種をそのまま確定分母にしない。

### 反証と変異試験

- 顔を既知量だけ過露出させた入力でS6が必ず失敗する。
- 無擾乱の基準画像で期待どおり再現する。
- 全体を暗くしてS6だけ通した候補は、全身輝度の退行門で失敗する。
- 無関係なUIシェーダを候補へ混ぜても因果候補として採用しない。

### 次段階へ進める条件

S6が1%以下になるだけでは足りない。全身輝度を大きく損なわず、候補コードから画素変化までの予測が一致し、S7〜S9へ新しい退行が無い場合だけ `artifact_measured` へ進む。

### 機械が決めないこと

残った肌の色味や印象が原作用途として許容できるか。これは代表比較を短く提示して人間が判断する。

## 契約 S8 — 髪の被覆

### 正解と現在値

- 正解資料: 原作 `h0157_32` と同構図のframe206、生え際ROI。
- 現在値: 髪被覆率比0.557。合格線0.67以上。
- 部位差: 前頭部 原作80.0% / 当方20.1%、側頭部L 93.9% / 30.9%、側頭部R 71.9% / 84.6%。
- 現在の段階: `scoped`。集計門はあるが、ランタイム入力が欠ける。

### 既に否定された説明

- アルファクリップ、面欠け、輪郭線殻、髪骨rest規約。いずれも実測で説明力が無いか悪化した。
- S6の白飛びだけが原因という説明。−1.5EVでも比0.52で回復しない。

### 因果接続に必要な証拠

- Helen本人のprefab root、髪renderer・submesh・材質対応、実行時髪物理の有無と入力。
- 頭髪の位置へ影響するコード、骨、物理パラメータの来歴。
- 候補が前頭部・左側頭部・右側頭部をどう変えるかという部位別予測。
- ローカル探索終了を主張する場合は、`f166` の修正版走査と実行時入力の棚卸しを完了する。

### 反証と変異試験

- 同一画像どうしでは合格する。
- 髪を後方へ既知量移動、または肌露出を増やした入力で失敗する。
- 集計値だけ改善しても、前頭部と左側頭部の欠落を別部位の増加で相殺した候補は採用しない。
- S6の白飛び改善だけでS8が動いた場合、髪ジオメトリ改善と呼ばない。

### 次段階へ進める条件

全体比0.67以上に加え、部位間の相殺を防ぐ補助門が必要。補助門の閾値は、原作フレームの再測定誤差を先に測ってから導出する。根拠なく新しい数字を置かない。

### 機械が決めないこと

髪の流れ、房の印象、左右差が原作用途として許容できるか。ただし、原因診断や全画像監査は人間へ戻さない。

## 契約 G10 — renderer・材質・RampSettingの対応

### 正解と現在値

- 正解資料: Helen本人のprefab rootから辿れる renderer → submesh → material → RampSetting の参照鎖。
- Rampの4帯とBlenderへの数値転写自体は検証済み。最大誤差0.00039、許容0.001。
- 現在の構造ゲートは14 PASS / 1 FAILで、残るFAILがG10。
- 現在の段階: `scoped`。Ramp値ではなく、Helenのどの部位へどれを割り当てるかの権威ある対応が欠ける。

### 既に否定された説明

- Blender既定の黒から白を残す案。原作ではbody・face・hairもRampMapを使う。
- 白で無効化する案。見た目は変わるが原作準拠ではない。
- 他キャラのbody Rampを名前や見た目だけで借りる案。候補にはなるが、忠実再現の確定対応にはならない。

### 因果接続に必要な証拠

- Helen SSR0101のprefab root、欠落材質、rendererとsubmeshの参照ID。
- RampSettingのbundle、path_id、materialの `_RampMap` 参照を直接つないだ鎖。
- ローカルに存在しないと主張する場合は、検索した全入力と未回収分母。
- 推測割り当てを試す場合は、忠実版と分離した `approximation` として別承認。

### 反証と変異試験

- 2部位のRamp割当を意図的に入れ替えたとき、参照鎖監査が失敗する。
- 既定黒白または白固定へ置換したとき、原作参照との一致門が失敗する。
- Rampサンプルを許容0.001より大きくずらしたとき、数値転写門が失敗する。
- ファイル名の類似だけで割り当てた候補を `confirmed` にしない。

### 次段階へ進める条件

参照IDで renderer → material → RampSetting が直接つながり、Blenderの対象ノードまで同じ対応を追跡できた場合だけG10をPASSにする。G10のPASSはS6・S8の合格を意味しない。

### 機械が決めないこと

権威ある入力が回収できない場合に、近似版へ切り替えるか。近似版は失う見え方を示して別承認を取る。

### H3 指摘台帳と完了阻止を作る

今回の4失敗を初期項目にし、`open` が残れば完了報告を止める。ユーザー指摘を同じ形で再依頼しない。

### H4 代表1件で通し試験

3契約の設計が揃った後で、最初の通し試験を1件だけ選ぶ。現時点の推奨は **S6 顔の白飛び**だが、まだ決定しない。S8は実行時物理、G10はprefab・材質入力が欠けるため、入口条件の比較後に選ぶ。

### H5 短い状態報告を生成

正本から、現在段階、通った関所、止まった理由、次の1件だけを自動生成する。長い手渡し資料を現行状態の代わりにしない。

## 捨てた案と理由

- 既存計画を全面改訂する案: 技術上の未完了点と、LLMの進め方の欠陥が混ざるため。

- 3欠陥を同時に実装へ流す案: 因果契約が有効かを確かめる前に作業量だけが増えるため。
