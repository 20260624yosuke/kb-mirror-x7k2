## 実測（画像認識は使っていない。テクスチャの画素値と座標だけ）

測り方: 成果物の build ログ `build-log-swimsuit.json` から**表示されている submesh を1件ずつ取り出し**、
そのメッシュの UV 座標で、割り当てられた PNG を引いて**中央値 RGB** を出した。
`R−B`（赤から青を引いた値）が肌の指標。原作の共有肌アトラス `shared-textures/body_d.png` は **+72**。

| 表示されている面 | 割り当てられたPNG | 中央値RGB | R−B | 判定 |
|---|---|---|---|---|
| 脚（P1_body_lod0.sub0・3312面） | `P1_body_d` | 193,194,195 | **−2** | **灰色。肌ではない** |
| 足先（P1_body_lod0_Dorm 2枚） | `P1_body_d` | 200,201,201 / 185,186,188 | **−1 / −3** | **灰色** |
| 首（body_lod0.sub0） | `body_d` | 231,164,144 | **+87** | 肌色 |
| 胴体（cloth2_lod0_Flat 4枚・8924面） | `cloth2_d` | 67,90,123 ほか | **−56 〜 −53** | **濃紺の布（＝ドレス）** |
| 髪 | `hair_d` | 72,83,105 | −33 | 布・髪として妥当 |
| 腰の布 3枚 | `P1_cloth_da` | 224,211,210 / 70,94,132 / 194,194,200 | +14 / −62 / −6 | 布 |
| **水着** | `swimsuit_da__derived` | 119,119,119 | **±0** | **無彩色。色が入っていない** |

### 1. なぜ肌が灰色なのか（原因は特定済み・憶測ではない）

`gf2-char-extract/scripts/ce_build_blend.py` の材質の割り当ては
**「名前が一致したらそのテクスチャを使う」が先**で、**肌の代替（共有肌アトラス）は名前解決に失敗した時だけ**
走る（`ce_common.skin_fallback_kind`）。対象は正規表現で
`SHARED_BODY_ATLAS_RE = _slg_(?:P1_cloth3|P3_body)(?:_|$)` の**2部位だけ**。

- ヘレンの脚 `P1_body` は自前の `P1_body_d`（512px・全面 197,197,197 の灰色）を**持っている**。
  だから名前一致が成立してしまい、肌の代替へ行かない。→ **脚と足が灰色になる。**
- 実測: `P1_body_d` は `__1`〜`__12` の13個すべて中央値 197,197,197。灰色でないものは1つも無い。
- 46件中、共有肌アトラスが適用されたのは **1件だけ**（しかもそれは非表示の面）。表示されている
  20件は全部「名前一致」。

**これは 2026-08-25 に一度出た指摘の再発。** `ce_build_blend.py` のコメントに
「武田さん指示『肌色が肌色じゃなかったので修正して』」と残っている。**そのときの直し方が
「産出側の正規表現に部位名を2つ足す」だけで、出力を測る検査を作らなかった。**
礼服版では脚はスカートに隠れていたので露見せず、水着で脚が出た瞬間に同じ症状が戻った。

### 2. 胸について — 表示されているのは胸ではなく「ドレスの胴体」

- 胴体帯（Y1.167〜1.478）にあるのは `cloth2_lod0_Flat` だけで、**4枚の submesh すべてが濃紺の布**。
  肌の submesh は**1枚も無い**（5枚目は面数0の空）。
- **ヘレンの lod0 には素肌の胴体メッシュが存在しない。** 体メッシュ（P1/P2/P3_body）は
  すべて **Y0.957（腰）で終わる**。Y0.96〜1.17 は腰布、Y1.17〜1.48 はドレス、Y1.48 以上が首と顔。
- 胸の張り出し（Y1.28〜1.36・中心から前方）の実測:
  **Flat 148.7mm / General 197.1mm / Bend 237.2mm**。台帳はこの数値を持っていなかったので、
  「段取りと違う種類」を機械が検出できなかった。
- 台帳 `visible-set-swimsuit.json` は `cloth2_lod0_Flat` を「胸（体型派生 Flat）」と書いていたが、
  **実体はドレスの胴体**。検査 D1 は台帳の名前と一致するかしか見ないので、**台帳が間違っていれば
  必ず通る**。

### 3. 水着が浮いて見える理由（数値）

- 水着の各頂点から胴体（`cloth2_lod0_Flat`）までの最近傍距離: 中央値 **12.1mm**、95% 点 28.9mm。
- 胴体側から見ると、水着から 5mm 以内にある胴体の点は **1.4%** しかない。＝**ほぼ接していない**。
- 高さ別の半径（中心からの距離）:
  Y1.20 水着48mm / 胴体117mm、Y1.25 水着143 / 胴体192、Y1.40 水着97 / 胴体141。
  **水着は胴体より内側**にある。つまり浮いているというより**ドレスの中に埋まっていて、一部だけ
  突き出している**。
- さらに水着のテクスチャは無彩色（±0）で、周りは濃紺のドレス。**色の関係が無い**ので異物に見える。
- 適合の相手として一番近いのは Flat（中央値 12.1mm）で、General 12.9mm・Bend 12.6mm。
  設計どおり Flat に合わせてはいるが、**その Flat 自体がドレスなので、合わせても水着姿にならない。**

## 監査に何が無かったのか（抜けの正体）

現行の検査 D1 は **「表示されているオブジェクト名の顔ぶれが台帳と一致するか」** だけを見る。
`plan_audit.py` は**計画書の書き方**を見る。どちらも**成果物の中身の数値を読んでいない**。

- 名前が合っていれば通る → 中身がドレスでも通る。
- 台帳が誤っていれば必ず通る → 台帳が「これは胸だ」と書けば胸になる。
- 色・接触・素肌の有無を測る検査が**1本も無い**。
- 「見えるようになった部位」（礼服では隠れていた脚）に、既存の関所が**適用されていないことを
  検出する仕組みが無い**。

## 変換した検査（V1〜V6・すべて画像認識を使わない）

| # | 名前 | 何を測るか | 合格線（案） | 今の値 |
|---|---|---|---|---|
| V1 | 肌の色 | 可視 submesh ごとに、実UVで引いたテクスチャの中央値 RGB | 役割=肌 は R−B ≥ +40 かつ R>G>B | 脚 −2 / 足 −1 → **FAIL** |
| V2 | 役割の実地判定 | 色・高さ帯・面積から役割を機械判定し、台帳の主張と突合 | 台帳と実地判定が全件一致 | 胴体「胸」対 実地「布」 → **FAIL** |
| V3 | 素肌の在庫 | 高さ帯ごとの可視面積を役割別に集計 | 胴体帯で 肌+水着 が既定比率以上 | 胴体帯 布100% → **FAIL** |
| V4 | 着衣関係 | 水着頂点から可視面までの符号付き距離の分布 | 接触帯に一定割合、埋没が一定以下 | 5mm以内 1.4%・内側 → **FAIL** |
| V5 | 変種の一致 | メッシュの変種語（Flat/General/Bend/lod）とテクスチャの変種語、胸の張り出し mm | 台帳の宣言と一致 | メッシュ `_Flat` にテクスチャ無印 → **FAIL** |
| V6 | 解決の台帳 | 可視 submesh 1行＝PNG名・sha256・中央値色・適用規約・役割・面積・高さ帯 | 全可視 submesh が1行を持つ | 未作成 |

**V1〜V5 のうち5本すべてが現成果物で FAIL する。** つまりこの6本があれば、この成果物は
武田さんの目に入る前に止まっていた。

## 工程の規則（再発を止める側）

- **R1**: 指摘が来たら、産出側の規則（正規表現・分岐）を直すだけで終わらせない。**出力を測る検査**を
  必ず1本足す。2026-08-25 の肌色の指摘はここで止まったため再発した。
- **R2**: 検査は台帳ではなく**成果物の数値**を読む。台帳が誤っていても落ちる検査であること。
- **R3**: 「今回から見えるようになった部位」を機械で列挙し、既存の関所の適用範囲に入っているかを
  確認する（礼服→水着で脚が露出した、が今回の抜け）。

## 決めてもらう必要があること

**ヘレンには素肌の胴体が存在しない。** これは実データで確定した事実で、方針を選ばないと
V3・V4 の合格線を数値で置けない（何に対して接触・被覆を測るかが決まらない）。
選択肢と代償は親メモの承認カードに記載した。
