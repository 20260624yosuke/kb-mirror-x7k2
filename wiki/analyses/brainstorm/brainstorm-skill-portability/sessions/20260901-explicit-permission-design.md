# 明示許可を承認イベントへ接続する修理方針 第1版

状態: 方針承認済み、詳細計画作成中。実装・実機検証は未実施。以下は修理案であり、現行機能の説明ではない。

## 2026-09-01 方針承認

実カードで「第1版方針を承認 (Recommended)」＋「はい、この選択でよい」を受領。明示許可の認識、対象付き保存、その記録による実装段階切替を一組で直す方針の承認として扱う。コード実行、Helen完成、一本化第3版、Blend変更の承認へ拡張しない。

## 目的と今回の判断

「この会話での実装を許可します」を、ユーザーの許可として受け取った事実と、機械の承認記録とで食い違わせない。
許可の対象・計画の版・会話を限定して記録し、その同じ記録で実装段階への案内を切り替える。
今回のカードはこの方針の採否。修理コードの実行承認・修理完了・Helen完成の承認ではない。

ユーザーの最新依頼:

> 承認イベントへ変換する解決法を考えます。
> 承認カードを出して。俺が承認と明言するまで会話を中断するの禁止

## 確認済みの原因と、まだ確認していないこと

1. Codexの `terminal_prompt` は発話全体が短い固定語と一致する場合だけ承認・中断を返す。「この会話での実装を許可します。」「先ほど、実装を許可と明言しました。指示に従ってください」「いえ、中断せずに実装をしてください。」は現在すべてNone（どちらにも分類しない）。
2. カード自由記述は選択肢の完全一致でなければ通常回答。独立した短い承認発話も、現在の判断対象への有効な結び付きがなければ承認状態にならない。
3. `operational_context` は通常作動時に「実装はせず、計画作成まで」を無条件で出す。認識語を増やすだけでは、この指示は残る。
4. `guard-write --lockdown` は `implementation_agent: separate-session` がある親だけを封鎖する。無条件の注入指示とは判定条件が違う。最初の実装保存の拒否は、許可不足ではなく別のready親メモの未読だった。
5. Claudeの現行SKILLは2026-08-31に旧禁止を撤回したと明記し、ユーザー指示があれば同じ会話で実装する。CodexのSKILLには旧禁止が残る。確認したのは仕様差であり、Claudeの実イベントとの比較試験はしていない。

Lunaの読取専用照合でも、上記3文は `terminal_prompt=None`、カード主回答＋確認「はい」でも `awaiting_card / next_card_required` だった。既存試験には、完全一致の承認／中断、確認不一致、自由記述の次カード要求、短い引用拒否はある。今回の正確な許可文、過去許可の再主張、否定を含む「中断せずに実装」、複数対象の許可は無い。これは試験棚卸しであり、修理の合格判定ではない。

## 修理案

### 1. 何の判断を待つかを先に固定する

既存の判断記録を再利用し、親メモ、独立した計画文書、その内容識別値（SHA-256）、判断の種類（方針／実行）、実装する会話の指定を結び付ける。方針の承認を実行へ変換しない。
同じ「承認」でも、親メモ選択・計画方針・監査コード実行・原作の見た目受入は別の判断である。

### 2. 明確な許可文を認識し、それ以外を黙って捨てない

最新のユーザー本人の独立発話について、全文一致の明示許可文を追加する。最低限「この会話での実装を許可します」「実装を許可します」を対象とし、現在の判断が一意な実行判断である場合に限って適用する。前後空白・末尾句点は既存と同程度に正規化する。

未登録の長文、引用、条件付き発話、対象が複数ある発話を、LLMの解釈だけで実行承認にしない。ただし許可の説明を単なる無回答にもせず、原文と未解決の対象を保持する。既存の有効な許可記録があるなら照合して維持し、同じ許可を取り直さない。無ければ、どの対象の許可かだけを一度の実カードで確認する。

カードの選択肢＋確認「はい」は既存どおり受理する。自由記述＋確認「はい」は明示許可文の同じ判定へ渡す。確認「いいえ」・確認欄の自由記述・部分回答・空回答では主回答を受理しない。

### 3. 保存した許可から実装段階を決める

承認語の検出だけで止めず、実際のユーザー入力／実カードの識別子、対象と版、許可の種類、会話指定を検証後に一つの許可記録として保存する。その記録を `operational_context` と成果物の書込み前検査が参照する。

- 計画・方針だけの承認: 実装には移らない。
- 有効な実行承認＋同じ会話の指定: その対象だけ実装段階の案内へ切り替える。
- 別の会話の指定: 指定を保持する。私が勝手に別会話へ変えない。
- 版変更・対象不一致・保存故障: 実行へ進めず、どの照合が失敗したかを記録する。既存許可を別対象へ流用しない。

SKILLの冒頭・承認後説明・注入文・書込み検査の条件を揃える。未読検査、品質ゲート、危険操作の権限まで解除する仕組みにはしない。
上位の実装禁止がその実行時点にも残るなら、承認イベントの成功と実装可能を分離し、反映経路を調査する。文書を書き換えただけで同じ会話の制約が変わったとは報告しない。

### 4. 既存の許可を失わせない

本会話のHelen監査第4版への「この会話での実装を許可します」は撤回されていない。今回の修理方針を考える間は保留であり、未承認へ戻したわけではない。
旧形式の許可は、元発言と対象版を実会話の識別子から一意に照合して移す手順を設ける。LLMが承認状態を手書きする方法は採らない。対象が解決できない場合だけ不足を明示する。

## 最低限の検証条件（実装段階で行う）

| 条件 | 必要な結果 |
|---|---|
| 一意な実行判断に明示許可文 | 対象・版付き承認が保存される |
| 方針判断中の「実装を許可」 | 方針から実行へ黙って飛ばさない |
| 「許可しません」、引用、条件付き、空回答 | 新しい承認が発生しない |
| 正しい主回答＋確認いいえ／欠落 | 主回答を受理しない |
| 別親・古い版・別カード・複数対象 | 誤った対象へ許可が移らない |
| 保存失敗、再読込失敗 | 実装段階へ進まない |
| 同じ許可の再送・圧縮後・次の入力 | 範囲を変えず保持し、再承認を求めない |
| 実フックでの同一会話の代表試験 | 認識・保存・注入・対象内の試験保存まで直接照合できる |

最後の試験は、隔離した対象で許可なし拒否・許可後通過・対象外拒否を確認する。合成入力や単体試験を実フックの成立と呼ばない。保存物・ログ・状態の対応まで検証してから使用可能と判断する。

## 実装前に詰めること

### 許可記録

新しい状態形式を別ファイルへ増やさず、既存セッション状態の `authorization` に次を保存する。

- `schema_version`: 1
- `status`: `active` / `invalidated`
- `permission_kind`: `execution`（方針承認はここへ入れない）
- `source_kind`: `card` / `terminal_text` / `legacy_event_import`
- `parent_path` と親パスSHA
- `decision_target_path` と内容SHA
- `implementation_agent`: `current-session` / `separate-session`
- `session_hash`、`turn_hash`、`input_sha`、カードなら呼出しIDハッシュ
- `accepted_at_ns`、失効時は `invalidated_reason`

生のユーザー文は状態へ複製せず、既存イベントログの入力SHAと対応させる。秘密や関係ない会話を増幅しない。

### 変更箇所

1. `codex_adapter.py`: 明示許可文を実行判断だけに分類し、カード自由記述にも同じ分類を使用。対象結合を検証して `authorization` を保存する。`operational_context` は有効記録と会話指定に応じて計画／実装の案内を選ぶ。
2. `brainstorm_guard.py`: 書込み前に同じ `authorization` の対象と版を照合する。既存の未読・品質ゲート・`separate-session` 封鎖を弱めない。
3. Codex版 `SKILL.md`: Claude版と同じ「実装先はユーザーが決める」外部仕様に揃え、方針承認と実行承認、同一会話と別会話を区別する。
4. tests: 純粋関数、状態遷移、旧状態互換、保存失敗、再注入、書込み前照合、実イベントの代表試験を追加する。`hooks.json` とClaude側は変更しない。

### 旧許可の移行

状態ファイルやカードイベントに有効な結び付きがあればそこから復元する。無ければ実会話ログの本人入力、対象計画SHA、同一ターンを一意に照合し、来歴付き `legacy_event_import` として一度だけ保存する。親メモの要約だけ、LLMの記憶だけ、現在の私の判断だけでは移行しない。一意に復元できない場合は許可が撤回されたとは書かず、機械移行未成立として保持する。

### 実装順と停止条件

R0 現行コード・状態・イベントログ・既存試験を内容SHAで固定。R1 許可分類と否定試験。R2 authorizationの保存・失効・再読込。R3 案内と書込み検査を同じ記録へ接続。R4 旧Helen許可を読取専用で一意性監査。R5 隔離対象で許可なし拒否・許可後対象内通過・対象外拒否。R6 実フックで入力・保存・注入・試験書込みの対応を直接照合する。

保存故障、対象SHA不一致、判断対象複数、旧許可の一意性不足、実フックと合成試験の不一致、既存未読検査の弱体化が一つでもあれば実装段階へ移さず停止する。既存Helen成果物、Claude版、hooks.json、config.tomlは変更しない。

指定モデルでの独立レビューを実装前に行う。Lunaへは文例の分類・既存試験の棚卸しなど境界を固定できる作業を渡し、承認範囲の最終判断は私が原資料と照合する。

Lunaへ渡した読取専用タスクは完了。コード変更・状態更新・フック呼出しは行っていない。
