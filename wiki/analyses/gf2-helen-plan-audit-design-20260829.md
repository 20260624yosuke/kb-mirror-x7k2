|---|---|---|---|

## 2. ボトルネックの正体

### 2.1 一言でいうと

**私が「作る側」と「測る側」を兼ねており、測る道具が作る側と同じ前提の上に乗っている。**
前提が誤っていると、道具は緑を返す。だから私の自己点検では前提の誤りが原理的に見つからない。

上の表の右端を見ると、**#3・#5・#6 という「前提そのものが違った」ものは、すべて外部（独立レビュー・
武田さんの問い）が見つけている。** 私が自分で見つけた #1・#2 は、どちらも「同じ前提の中での計算ミス」
だった。**種類が違う。**

具体例:

- **#5（21部品 vs 6部品）**: 私は生の頂点番号で連結成分を数えた。判定 G7・G8・G9b も同じ生の
  頂点番号から辺と面を作る。**同じ表現を使っているので、どちらも縫い目を見ない。**
  結果、上衣が最大100mm 裂けていても「辺10倍超0 ○ / 裏返り0 ○ / 二面角0.998 ○」が出る。
- **#3（G10）**: 試験の初期値が正解と一致する作りだったので、手順の中身が何であれ0mm を返した。
  **試験と手順が同じ前提（scale=1.0・同じ体）を共有していた。**

### 2.2 二番目の原因

**結論に「これが誤りならどこで分かるか」を書かずに出していた。** 反証の条件が無いので、
反証は誰かが偶然、別の出発点から測ったときにしか起きない。だから覆るタイミングが読めず、
議論が進んだ気になってから戻る。

### 2.3 三番目の原因

**記録は追いついているが、記録された結論を守る機械が無い。** メモには全部書いてあるが、
次のターンで前提が動いても、止めるものが無い。武田さんが毎回読んで気づくしかない。
これは前回の分析（`llm-review-bottleneck-applied-2026-08-28.md`）が
「最大のギャップ = #9 人間の指摘が機械判定に変換されていない」と書いたことの再発。
**却下案の JSON 化だけは実装されたが、それ以外は文章のままだった。**

### 2.4 ボトルネックではなかったもの

- 解析能力・データ不足ではない。数値は毎回取れている（独立レビューでも section 2.1〜2.3、
  原作10組の40セル、現行結果9行が再現された）。
- 記録の不足でもない。撤回はすべてメモに残っている。
- **足りないのは「前提が違っていたら赤くなる仕掛け」だけ。**

## 3. 監査の設計（この案件に要るものだけ）

一次資料の判断基準は「**これを入れると武田さんが確認しなければならないものは具体的に何個減るのか**」。
上の6件は全部、武田さんか外部レビューの手を煩わせた。そこを直接減らす形にする。

### 3.1 中核の考え方 — すべての関所は「落ちること」を先に証明する

今回いちばん高くついたのは #3（落ちない試験を合格の根拠にした）。これは1件の事故ではなく、
**関所一般に起きうる**。したがって監査の第一原則を次のようにする。

> **合格を名乗ってよいのは、その関所が「壊した版」を実際に落とせたことを示せる場合だけ。**

実装は変異試験（mutation test）。判定対象のコードに、あらかじめ決めた壊し方を機械的に施した版を作り、
関所が落ちることを確かめる。**1つでも落ちない壊し方があれば、その関所は無効として扱う。**

### 3.2 監査項目（過去の失敗と1対1で対応させる）

`tools/plan_audit.py`（新規・未実装）に入れる。各項目に「**この項目が見ていないもの**」を必ず書く。

| 記号 | 由来した失敗 | 判定 | この項目が見ていないもの |
|---|---|---|---|
| **A1** | #1 測り方の不一致 | 判定経路で使う距離関数が1つだけであること。例外（G3b の最近傍距離）は計画書に明記されたものだけ許可し、コードの実使用箇所と突合 | 距離関数が1つでも、その関数自体が誤っている場合 |
| **A2** | #2 合格させる調整値 | `fit` 系の呼び出し定数をコードから抽出し、計画書の記載と一致すること | 計画書のほうを書き換えて合わせる回避 |
| **A3** | #3 検出力ゼロの試験 | **変異試験。** 指定の壊し方（最低4種）で関所が落ちること | 壊し方の種類に無いバグ |
| **A4** | #5 生インデックスで数えた | 位相（連結成分・辺・開いた辺）を数える箇所が溶接後であること。かつ縫い目のずれを測る項目が判定に含まれること | 溶接の丸め桁の選び方が不適切な場合 |
| **A5** | #6 合格線の出どころ | 合格線を産むスクリプトが `tools/` にあり、その出力が計画書の表と数値一致すること。**組数も一致すること** | スクリプトと計画書の両方が同じ誤りをしている場合 |
| **A6** | 役割規則が排他でない | 規則を実データへ適用し、各部品にちょうど1つの役割が付くこと。順序依存なら適用順が計画書に明記されていること | 規則そのものの妥当性 |
| **A7** | 却下案の再提出 | 既存 `rejected_approaches_check.py`（否定文の除外を修正したうえで） | 「禁止と書きながら実際にやる」計画 |
| **A8** | 証拠なしの完了 | 各完了条件に、対応する出力ファイルの存在と生成時刻があること | ファイルの中身が正しいか |

### 3.3 3種類への分解（一次資料 8節）

| 種別 | 担当 | 中身 |
|---|---|---|
| **A 決定論的** | `tools/plan_audit.py` | 上の A1〜A8。**武田さんは結果の1行だけ見る** |
| **B 限定 LLM 監査** | サブエージェント | 役割を3つに限定する（前回分析と同じ）: ①却下済み方針への抵触 ②証拠なしの完了扱い ③記述と実ファイルの矛盾。**「全体をレビューして」とは言わない** |
| **C 人間判断** | 武田さん | 目的への合致、トレードオフの選択、意匠（水着に見えるか）。**それ以外は返さない** |

今回のサブエージェントは「仕様と実装の不一致を重点的に」で投げたので B の形に近かったが、
**A1〜A8 として機械化できるものまで LLM に探させていた。** 機械へ移す。

### 3.4 報告の形（一次資料 14節）

Phase 完了時に武田さんが最初に見るのは次だけにする。

```
Phase n 完了
自動監査   8 / 8 PASS
変異試験   4 / 4 検出
人間判断が必要  1件 → <論点>
詳細  必要なときだけ
```

### 3.5 継続改善（一次資料 12節）

Phase が終わるたびに、その回に武田さんが出した指摘を棚卸しし、
「決定論的へ移す / 限定 LLM 監査へ移す / 人間判断として残す」へ振り分ける。
**振り分けた結果を `plan_audit.py` の項目表へ追記する。** ルールは無制限に増やさず、
実行時に読ませる知識ではなく外部の検証として持つ。

## 4. 導入しないもの

- CI・pre-commit・大量の hook。単独作業なので維持コストだけ増える（前回分析と同じ結論）。
- レビュー用エージェントの追加。読む文章が増えるだけ。既存を狭めるほうが効く。
- 契約 JSON を大量に作る構成。トークン有限の制約に反する。

## 5. 未確定・この分析が見ていないもの

- `plan_audit.py` は**未実装**。設計だけ。
- 変異試験の「壊し方」の一覧は、案P の実装が決まらないと確定しない（今ある4種は案N 用）。
- **A1〜A8 をすべて通しても、案P の設計自体が正しい保証はない。** 監査は過去の失敗の再発を
  止めるもので、新しい種類の失敗は止められない。
- この分析自体が、私（作る側）が書いている。**同じ構造の問題を持つ。**
  A3（変異試験）を最初に実装し、この監査自体が落ちることを確かめるのが最優先。
