# Eグルの類似判定(vector-db)の仕組み分析と、パーソナライズ・フォルダ振り分け構想

## このセッションの位置づけ

2026-07-02、武田さんが「ある程度文脈がある中でEグルの仕組みを分析・理解してほしい」という目的で、
X→Eグル重複処理の作業セッションから**フォークした会話**で実施した分析。目的は、フォルダ振り分けの
skill を作るための土台として、Eグルが画像をどう認識・類似判定しているかを実地で理解すること。
このページはその分析結果と、そこから出た構想の記録。

分析部分(## Eグルの類似判定の仕組み)は Eグルライブラリの実データを直接読んだ source-backed。
構想部分(## フォルダ振り分け / ## パーソナライズ構想)は AI とユーザーのアイデアで、まだ試作も
していない inferred。

## Eグルの類似判定の仕組み(実地調査・source-backed)

Eグルライブラリ `.../2024_11_16_eagle_フォルダ管理.library` を読んで確認した。

### ベクトルDB(vector-db)

ライブラリ直下に `vector-db/` があり、3種類の埋め込み(embedding=画像や文字を数値ベクトルに
変換したもの)を持つ。いずれも SQLite 形式の `vectors.db`。

- `embedding-image`(86MB, **384次元**) — 画像の見た目をベクトル化
- `embedding-title`(47MB, 128次元) — ファイル名をベクトル化
- `embedding-metadata`(36MB, 128次元) — タグ・メモをベクトル化

`embedding-image/vectors.db` の `vectors` テーブルは **34,811行**(ライブラリ約34,827枚にほぼ対応)。
各行は:

- `vector_id`: `<eagle_id>-image`(例 `MMU5J6C9Z66L7-image`)
- `vector_data`: 1536バイトの BLOB = **384 × float32**(全行が1536バイトで統一)
- `metadata_json`: `eagle_id`、`image_signature`、`updated_at`

`image_signature` は `<ファイルサイズ>-<幅>-<高さ>`(例 `1570909-2764-4040`)。**Eグル自身も、
ファイルサイズ+寸法で画像を見分けている**。これは X→Eグル拡張の v0.5.34 で重複対策として実装した
「ファイルサイズ→sha256」照合の前段と同じ発想。関連: [[x-eagle-duplicate-existing-item-discard-fix-2026-07-01]]。

`.ai-search-config.json` は `indexingEnabled: true`。各 embedding の設定は
`index_type: "Flat"`、`metric: "IP"`(Inner Product = 内積)。全文検索用の `eagle_items_fts`
(fts5, trigram, title/tags/annotation/folder_names)も同居している。

### 各検索コマンドが使っているもの(整理)

- **「画像マッチ」「Find by Media」「セマンティック(画像)」** = 384次元の画像ベクトルの内積
  (コサイン類似度に相当)で近い順に並べる。クエリ画像も同じモデルで384次元化して全画像と比較。
  「Find by Media」の `Min 65%` / `Results 20` は、この内積のしきい値と件数の調整。
  「画像マッチ」と「Find by Media」は入口・UI が違うだけで、土台の vectors.db は共通と見るのが自然
  (Eグルの画像類似の基盤はこの vectors.db 一つ)。厳密にどちらかが別方式(知覚ハッシュ等)である
  可能性はゼロではない。
- **「カラー」** = 各画像 `metadata.json` の `palettes`(色と割合)。
- **「形」** = `width`/`height`(縦横比)。
- **キーワード** = `eagle_items_fts`(全文)+ embedding-title / embedding-metadata。

### sha256指紋 と vectors.db の違い(ユーザーの問いへの回答)

武田さんの問い「sha256のような指紋よりも、画像のデータを抽出できるということ?」への回答。

- **sha256指紋** = 「1バイトも違わず完全に同じか」だけを判定する。似ているかは一切分からない。
  同一画像の重複検知専用。
- **vectors.db の384次元ベクトル** = 「どんな絵か」の要約。似ている度合いを連続量で測れる。
  用途が根本的に違う。武田さんの理解「指紋より豊かな、画像内容の抽出」は正しい。

## フォルダ振り分けskillのアイデア

Eグルが全画像を384次元ベクトルにして vectors.db に保存済みなので、それを読むだけで類似検索を
自前で計算できる(モデルを自分で走らせる必要がない)。

### 中核アイデア: 似た画像への「相乗り」(k近傍)

未整理の1枚について、vectors.db で似た既存画像トップ20を探し、その20枚が入っているフォルダを
集計して、一番多いフォルダを振り分け先として提案する(k近傍分類)。武田さんの既存フォルダ分け
そのものが教師データになるため、他人の基準でなく武田さん自身の分類傾向に沿った提案になる。

### 二軸の得意・不得意([[eagle-folder-prediction-pilot-2026-06-14]]の結論と一致)

- **得意=視覚テーマ軸**(構図・季節・人体・服装・色): 画像ベクトルがそのまま効く。
  例: 01_カラーラフ / 03_人体 / 04_季節。
- **苦手=出自軸**(作者・キャラ・作品): 画像ベクトルでは弱い。ファイル名(`x-<作者>-`)や
  メモ(注釈の author_id)で補う。例: 07_作品_NIKKE / 02_絵柄_<作者>。

### 現実的な第一歩: 精度を先に測る試作

いきなり全部作らず、振り分け済みの画像を「もし未整理だったら」として似た画像トップ20から
振り分け先を当てられるか答え合わせする。数十枚回せば、得意不得意が数字で出る。skill の形
(どこまで自動、どこから保留)は、当たる範囲が見えてから決める。多数決がバラける画像は
「自信なし」で保留に回す誤振り分け防止ゲートを付ける。

## パーソナライズ構想(フォルダ傾向 + Canvas)— ユーザー提起・意図一部未確定

武田さんの問い「vectors.db は、私のフォルダ振り分けの傾向 + KB内 `raw/_MY_ART` の Canvas データを
元に、パーソナライズした情報を体系化して、フォルダ分けしきれていない画像へフォルダ振り分けskillと
してフィードバックできるか?」への現時点の整理。

- **フォルダ振り分けの傾向を学習**: 上記 k近傍がまさにこれ。武田さんの既存フォルダ分けが教師。
  実現性は高い。
- **`raw/_MY_ART` の Canvas データの活用**: ここは意図の具体像が未確定。Canvas は制作中作品の
  参考画像・ラフ・メモのボードで、「武田さんが今何を作ろうとしているか」の文脈を持つ
  (raw/_MY_ART は制作中作品の常用作業フォルダ。[[art-canvas-ingest-design]]、[[myart-canvas-gallery]])。
  振り分けにどう効かせたいかで設計が変わる
  (例: 今の制作テーマに近い未整理画像を優先的に拾い上げる/Canvasの傾向を新しい分類軸にする 等)。
  次セッションで武田さんに確認する。

武田さんは「今までの開発規模より少し大きなプロジェクトになりそう」と規模感を認識している。

## 制約・未確定

- 新規保存した画像は、Eグルが裏でベクトル化を終えるまで vectors.db に入らない(時間差)。実際、
  2026-07-02時点で当日保存の `MR1KJ60OZKL0B` はまだ vectors に存在しなかった。
- 使用モデルは非公開。自前で新規画像を同じ空間にベクトル化するのは難しく、Eグルの計算完了を
  待つのが現実的。
- vectors.db はEグルが書き込む。skill は読み取り専用で扱う(Eグル稼働中の直接書き込みは危険)。
- 「振り分け先の提案」までは HTTP API 非依存で可能だが、実際にフォルダへ入れる操作は、Eグルの
  公開 HTTP API に既存項目のフォルダ変更機能がないため別手段が要る(この制約は同日の
  [[x-eagle-duplicate-existing-item-discard-fix-2026-07-01]] で判明済み)。
- Canvas 連携の具体像は未確定(上記)。
