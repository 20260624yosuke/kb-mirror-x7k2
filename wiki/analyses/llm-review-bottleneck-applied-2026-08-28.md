# レビュー・検証ボトルネック論を Helen水着化プロジェクトへ適用する

## このページの役割

ChatGPT と検討した「AIエージェントで実装が速くなった結果、人間のレビュー・検証が新しい
ボトルネックになる」という論を、[[gf2-dusevnyj-p3-bikini-to-helen-handoff-20260827]] の
現行計画へ当てはめた分析。**資料に書いてあるものを全部入れるのではなく、この案件に要るものだけを採る。**

一次資料は上記 frontmatter の2ファイル。要点は「AIにもっと仕事をさせる」ではなく
「**人間が確認しなくても済む条件を増やす**」こと。判断基準は
「**これを入れると武田さんが確認しなければならないものは具体的に何個減るのか**」。

## 1. 現状評価（資料 16.1 の対応表）

| # | 項目 | 状態 | 実際の根拠 |
|---|---|---|---|
| 1 | 大きな計画と小さな実行単位の分離 | **部分的** | Phase 0〜4 はあるが Phase 1 だけで source / component / target-body / pose の4監査を抱える |
| 2 | Phase単位の作業 | 既に存在 | handoff section 7 |
| 3 | Phaseごとの明確な完了条件 | **部分的** | Phase 4 の `harness-ready` は定義があるが、Phase 1〜3 は「台帳化する」「記録する」で終わり、機械が合否を出せない |
| 4 | セッション分離 | 既に存在（運用が守れていない） | handoff 方式はある。だが 2026-08-28 の会話は圧縮で武田さんの意図の粒度が落ちた |
| 5 | 状態ベースの引き継ぎ | **既に存在・資料より先行** | handoff は revision 制で、承認状態の表・却下案の表・実測値まで持つ。資料7節が求めるものをほぼ満たす |
| 6 | 決定論的な検証 | **部分的** | `tools/project_quality_gate.py` の plan/batch/complete は存在。ただしミティール案件で「監査自体が構造的に見逃す」と判明済み |
| 7 | LLM監査の役割限定 | **不足** | 独立監査役の役割が「原本・fixture・生測定から別経路で再計算」＝何でも監査。資料10節が警告する形そのもの |
| 8 | 人間判断事項の抽出 | 部分的 | 「差を1〜4件に絞ってから提示」は明文化済み |
| 9 | 人間フィードバック→検証ルールへの変換 | **存在しない（最大の欠落）** | 却下理由は handoff の表に**文章でしか**書かれておらず、機械が再提出を止められない |
| 10 | hook等による検証強制 | 部分的 | `brainstorm_guard.py` と quality-gate は動く。ただし止められるのは書き込み先だけで、計画の中身は止まらない |
| 11 | レビュー結果の認知負荷削減 | **不足** | 計画は毎回1枚の大きな文書として提示され、4回とも不承認 |
| 12 | Phase完了ごとの継続改善 | 存在しない | 棚卸しの仕組みが無い |

## 2. 最大のギャップ

**#9（人間の指摘が機械判定に変換されていない）。**

証拠: 2026-08-28 のセッションで計画が4回提示され4回とも不承認になった。却下理由は
handoff の section 0.2 に表で残っているが、**次に計画を書く LLM がそれに抵触しても、
止めるものが何も無い**。だから武田さんが毎回自分で読んで、自分で「これは前に却下した方向だ」と
判定する必要があった。これはまさに資料12節の言う「同じレビューを人間が二度している」状態。

ここを直すと、武田さんが確認しなければならないものが最も多く減る。

## 3. 自動化候補（人間確認 → 決定論的チェックへ）

今の計画で武田さんが目で確認する前提になっている項目のうち、機械の PASS/FAIL に落とせるもの。

| 現在 武田さんが確認していること | 機械判定への置き換え |
|---|---|
| 却下済みの方向の計画をまた出していないか | `rejected-approaches.json` に却下案の判定条件を書き、計画提出前に自分で照合する。抵触したら提出しない |
| 計画が大きすぎないか（トークン有限） | 計画の項目数・生成ファイル数の上限をゲート化 |
| トルソーだけになっていないか | 成果物の Y 範囲が Helen 全身域（およそ 0.16〜1.69）を覆っているかを判定 |
| 腰に穴が開いていないか | 溶接後の開いた辺の連結成分の最大寸法。2026-08-28 の計測スクリプトがそのまま使える |
| Flat を General/Bend へ取り違えていないか | 使用 mesh の SHA-256 と面数・頂点数の照合 |
| 原本を壊していないか | 入力 Blend / npz の SHA-256 照合 |
| 画像判読を根拠にしていないか | run manifest に画像判読由来の根拠を書けなくする（[[llm-vision-review-suspension-policy]]） |
| 証拠なしに完了扱いしていないか | 各完了条件に、対応する出力ファイルと生成時刻の存在を必須化 |

このうち「腰の穴」「SHA照合」「Y範囲」は、**すでに手元で動く計測方法があり、新規開発がほぼ要らない**。

## 4. LLM監査の再設計

現状の独立監査役は「何でも監査するAI」で、資料10節の警告どおり**武田さんが読む文章を一段増やす**
だけになりかねない。次の3つに絞る。

1. **却下済み方針への抵触だけを探す**（handoff section 0.2 と `rejected-approaches.json` を突き合わせる）
2. **証拠なしに完了扱いしている項目だけを探す**
3. **handoff の記述と実際のファイル状態の矛盾だけを探す**

これ以外（全体の妥当性、設計の良し悪し、見え方）は LLM 監査の担当にしない。

## 5. 継続改善ループ

Phase が終わるたびに、その回に武田さんが出した指摘を棚卸しし、次の3つへ振り分ける。

1. 決定論的チェックへ移せる → `rejected-approaches.json` / ゲートへ追加
2. 限定 LLM 監査へ移せる → 上の3役割のどれかへ追加
3. 人間判断として残す → handoff に「人間に残る判断」として明記

**ルールを無制限に増やさない。** 実行時に毎回読ませる知識（＝コンテキストを食う）と、
外部の決定論的検証として持つもの（＝コンテキストを食わない）を分け、後者を優先する。

## 6. 計画への反映案

- Phase 1 を1本ずつに割る（現状の4監査同時は、武田さんが一度に読む量が多すぎる）。
- 各 Phase の完了条件を、動詞ではなく**存在するファイルと通るチェック**で書く。
- 却下案を文章の表から機械が読める JSON へ移す。
- 報告の形を資料14節の形式（目的 / 変更 / 自動検証 n/n PASS / 人間判断が必要 1件 / 詳細は必要なときだけ）
  に変える。

## 7. 導入しない方がよいもの

- **CI / pre-commit / 大量の hook**。この案件は共同開発ではなく単独の Blender 作業で、
  維持コストだけ増える。
- **Reviewer Agent の追加**。読む文章が増えるだけ。既存の独立監査役を狭めるほうが効く。
- **Phase ごとの新セッション強制**。handoff が既にその役割を果たしている。運用で足りる。
- **契約 JSON 12本の構成**（handoff section 6 の案）。トークン有限という制約に正面から反する。
  上の自動化候補は3〜4本の JSON で足りる。

## 矛盾・未確定

- 本ページは提案であり、**武田さんの承認を受けていない**。実装もしていない。
- 「却下案を JSON にすれば再提出が止まる」は未検証。判定条件を言葉でどこまで書けるかは、
  実際に section 0.2 の6件を JSON へ落としてみないと分からない。
- ミティール案件で「監査自体が構造的に見逃す」ことが起きているため、決定論的チェックを増やすこと自体が
  安全を保証しない。**何を測っていないか**を各チェックに書き添える必要がある。
