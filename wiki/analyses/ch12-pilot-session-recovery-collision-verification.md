# ch12 パイロット時のセッション停止復旧・二重作業衝突・独立検証の記録

の session/part テーブル照会)、gate 出力、ファイル mtime 等の当日直接観測(本セッションで取得)。

## 1. サブエージェント結果の喪失と opencode DB からの復旧

**何が起きたか**: 親セッション停止により batch4 再試行(`ses_fd58654e0ffeEMjQlZCtAfbZzi`)の完了結果が
親に返送されず「失われた」状態になった。ただしサブエージェントは親と独立したセッションとして動くため、
完了していれば本文が `opencode.db` の part テーブルに残っていた。SQL で抽出し 15 枚中 9 枚分の観測本文を回収。
残り 6 枚(13m10s〜14m20s)+ 切断された 14m52s は観測ブロック自体が存在しないことを確認したうえで、
一時 dir に現存する PNG から新規サブエージェントで再読取して補完した。

**落とし穴(実害)**: task 出力にはプロンプト部のファイルパス一覧も含まれるため、正規表現で
「ファイル名の言及」を集計すると prompt echo まで数えて過大評価になる。初手で「15枚全回収」と誤判定し、
観測ブロック単位で再集計して初めて欠落 7 枚が判明した。

**バッチ展開時への適用**:
- 親セッションが死んでもサブエージェントの成果は DB 残留の可能性が高い。export JSON だけで諦めず
  `session_id` を頼りに part テーブルを照会してよい。
- 回収判定は「観測ブロック(`<ファイル名>` + 確信度 + 観測文)の有無」で行う。ファイル名言及の集計は不可。
- 一時 dir のフレーム PNG が生きている限り、読み直しは数分で済む(抽出のやり直しは不要)。

## 2. 同一成果物への二重作業衝突(ハーネス違い)

**何が起きたか**: desktop 側の旧セッションと CLI 側の本セッションが、同じ manifest / source 観測節 /
frames dir に向かって同時に書き込みを進めた。旧側は 04:05–04:48 に manifest.json(47 観測)・観測節挿入・
`tools/video_ingest_gate.py` 修正・recheck 起動まで到達。CLI 側は盲検読取完了後、フレーム 48 枚を
保存しようとした時点で manifest の新規出現(mtime 04:08)により衝突を検知した。

**対応(結果的に破損ゼロ)**:
1. CLI 側は manifest / source / index / log への書き込みを全面停止(いずれも未着手だった)。
2. 自分が置いたファイルのうち相手の manifest 非参照分 15 枚のみ削除し、frames dir を
   相手の manifest 参照 47 枚と完全一致させた(孤児フレームによる相手の gate FAIL を防止)。
3. ユーザーへ状況を提示して継続役を確認(回答は「CLI が引き継ぐ」だったが、確認時点で旧側は完走済みのため
   実質的に CLI は検証役へ移行)。

同一名のフレームは両者とも同じ一時ソースからのコピーなので byte 一致であり、内容破壊は発生しなかった。

**バッチ展開時への適用**:
- ハーネスが違っても vault と opencode.db は共通。作業開始時に (a) 対象ファイル群の mtime、
  (b) opencode.db の session 更新時刻、を確認し並行 writer の有無をチェックする。
- 衝突検知時は「自分の footprint(相手が参照しない自分の生成物)だけ撤去 + 書き込み退避」が最短解。
  相手の編集物を削除・上書きしてはならない(AGENTS.md 併用ルールどおり)。
- ユーザーが複数ハーネスに同じ指示を出している可能性は常にある。曖昧なら作業前に確認を取る方が安い。

## 3. 独立検証(第三読取による不一致決着)

**何をしたか**: 完成済み成果物に対し、①`check --phase complete` を CLI 側から再実行(**PASS**)、
②独自に収集した 105 枚全件の盲検読取データと観測表 47 行を照合、③照合で見つかった不一致 1 ブロックを
第三の盲検読取で決着。

**不一致の内容と決着**:

| フレーム | 成果物の表 | CLI 側の独立読取 | 第三読取の決着 |
|---|---|---|---|
| hizurume-ch12-01-13m33s.png | 蜂スライド(視覚心理) | 調和対比スライド(誤読) | **蜂スライド**(3票対1票) |
| hizurume-ch12-01-14m52s.png | 力場+密度分布スライド | 蜂スライド(誤読) | **力場+密度分布**(2票対1票) |

決着の結果、**成果物の表は正しく、誤っていたのは CLI 側(検証側)の 2 読取**だった。
誤読の原因特定はしていない(推測の域を出ないため事実記載をしない。強いて傾向を言えば、
13m33s 誤読は直前フレーム群との連続性仮定、14m52s 誤読は同バッチ内で 13m33s 相当の画像を
先に読んだことの混線可能性がある — いずれも uncertain)。

**バッチ展開時への適用**:
- 落とし穴 #7(誤観察率 2〜3 枚/52 枚)の再確認。単独読取の誤りは検証側でも起きる。
- 不一致の決着手段として第三の盲検読取(多数投票)は低コストで有効。クロップ確定が必要なのは
  字形レベルの争点だけで、スライド同一性レベルなら丸読み 1 回で足りる。
- 独立検証データは「完成物の裏取り」として機能した。バッチ展開でも統括側とは別系統の
  読取データ(または最低限 recheck 以外のスポット再読取)を残す価値がある。
