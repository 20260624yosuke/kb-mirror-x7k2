## 4. 共通欄ファイル `run-state.common.json`

### 4.1 なぜ別ファイルにするか

既存の記録ファイル（`run-state.json` 等）に欄を足す方式は、次の理由で採らない。

| 既存ファイルに足す場合の問題 | 別ファイル方式での解消 |
| --- | --- |
| `json.load` → `json.dump` で全体を書き直すため、キー順・インデント・非 ASCII エスケープ・改行が変わる。helen は 129,913文字の日本語が入り、既存の grep 前提スクリプトが壊れうる | **既存ファイルを1バイトも触らない** |
| 複数セッション並行で読み込み→全体書き戻しすると後勝ちで消える | 書き込み対象が別ファイルになる |
| 既存の `blocked` と語彙が違う2本が同居する | 同居しない |
| バックアップの置き場が判定の対象に入る | バックアップ自体が不要 |

> rev.4 は相手の `audit/state.json` を唯一の機械入力にしていたが、**武田さんの裁定（軸②優先）により
> 撤回した**。相手の実装（P0B）待ちでは軸②が進まないため。
> 相手が `state.json` を作った後は、`common.related.data[]` から参照するだけにする。

### 4.2 スキーマ（判定②が読む入力の全部）

```json
{
  "schema": "run-state.common/1",
  "project_slug": "gf2-helen-repro",
  "updated_at": "2026-08-31T12:34:56+09:00",
  "source_files": ["/絶対パス/run-state.json"],
  "current_step": "E（検証）40回目",
  "gates": {"passed": ["G1"], "failed": ["G10"], "source": "/絶対パス/logs/f152-visual-gates.json"},
  "artifacts": [{"path": "/絶対パス/blends/helen-h0157-repro.blend",
                 "sha256": "04ef8b79…", "mtime": "2026-08-25T17:29:00+09:00"}],
  "blocked": [{"id": "B01", "item": "…", "state": "blocked", "why": "…", "evidence": "/絶対パス"}],
  "next_choices": [{"label": "A", "what": "…", "cost": "…"}],
  "related": {
    "projects": [{"name": "ヘレン水着化", "root": "/絶対パス"}],
    "handoffs": [{"path": "/絶対パス", "status": "current"}],
    "data":     [{"path": "/絶対パス", "note": "…"}]
  },
  "history_ref": {"file": "/絶対パス/run-state.json", "key": "history", "count": 113}
}
```

- **生成側（判定②）はこのファイルだけを読む。** 案件ごとの読み取り規則を持たない。
- 欄が欠けていたら**生成を止める**（部分生成しない）。欠けている欄名を出す。
- `blocked[].id` は archive の重複判定に使う（3.6）。
- `history_ref.key` は `null` を許す（ふたなり化・キャラ抽出に `history` キーは存在しない）。

### 4.3 共通欄ファイルの維持

- **書くのは、その案件で作業する LLM。** 判定⑥（ずれ検知）が更新を促す。
- **中身の正しさは機械では判定できない**（`current_step` や `gates` の内容）。11節-1 に残す。
- `verify` で照合できるのは、SHA の再計算・パスの実在・件数の再計測まで（8節）。

## 6. 案2（既存ページ側からの戻り道）— 仕組みだけを作る

- **仕組みは本計画で作る。helen の既存7枚への適用は 14節の整理タスクが行う。**
- 対象の出所: `common.related.handoffs[]` のみ。
- **ブロックは機械が書く。** `status` の出所は `related.handoffs[].status` のみ。

```markdown
<!-- current-state-pointer:start -->
> [!info] この案件の入口
> 現在位置は `wiki/builds/<slug>-current-state.md` が入口。このページは経緯の記録。
> 現行/旧: **旧**
<!-- current-state-pointer:end -->
```

- **「正本」という語を使わない**（4回目レビュー D-2 への対処）。
  壊れ#4 の残存検査は抽出語 `正本` / `こちらが新しい` / `現在位置` / `最新` / `正規入口` を使うため、

## 8. `verify` の仕様

`verify <slug>` は生成物と入力を照合する。1つでも不一致があれば非ゼロ終了する。

| # | 照合するもの | 方法 |
| --- | --- | --- |
| 1 | マーカー内の各値 | 共通欄の対応値と一致するか（切り詰め時は archive との合計で照合） |
| 2 | `artifacts[].sha256` | 実ファイルの SHA-256 を再計算して一致するか |
| 3 | `artifacts[].mtime` | 実ファイルの mtime と一致するか（**秒単位に丸めて比較**） |
| 4 | `blocked[].evidence` / `gates.source` / `related` の全パス | 実在するか |
| 5 | `history_ref` | `file` が実在し、`key` があればその要素数が `count` と一致するか |
| 6 | 節5 | 3.5 の書式を満たすか（データ行のみ） |
| 7 | マーカー | `start`/`end` が**6組**そろっているか |
| 8 | archive | 節8から移した項目が `blocked[].id` 単位で全部あるか（落ちていないか） |

- **照合できないもの**: `current_step` と `gates` の**内容**が実態と合っているか（11節-1）。
- **`answer-key <slug>`**: 9.2 の正解表を出力する。内容は
  「`current_step`」「`blocked[]` のうち `state != done` の全件」「`next_choices[]` の全件」。
  出力先は **`<KBルート>/logs/answer-key-<slug>-YYYYMMDD.md`**（`work_roots` の外）。
