## 見つかった不具合と修正（2026-08-03）

### 不具合: 脚のひざ・足首が曲がらない（武田さんの指摘「足が動いてなくね？」）

**原因**。載せ替えスクリプト `helen-retarget-game-motion.py` は、ポーズボーンの拘束を
**種類を選ばず全部ミュート**する（同スクリプト 336–341行）。そこには MMD の
**付与親**（親ボーンの回転を別のボーンへ渡す仕組み。`mmd_additional_rotation` と
その入力を作る `mmd_tools_at_dummy`）まで含まれていた。

ミティールの脚メッシュは **`左足D` / `左ひざD` / `左足首D` にしかウェイトが無い**
（実測ウェイト合計: 左足D 863.7 / 左ひざD 900.2 / 左足首D 959.1 に対し、
`左足` `左ひざ` `左足首` は **すべて 0.0**）。D ボーンは付与親で `左足` などから回転を
受け取るので、付与親を止めると **アニメーションは `左足` に入っているのに、見える脚は
それを受け取らない**。結果、脚は「下半身から生えた 1 本の棒」として腰と一緒に振れるだけで、
ひざも足首も曲がらない状態だった。

**私の以前の回答は誤りだった**。「足首の移動量 0.70cm だから正しい」と報告したが、
測っていたのはウェイト 0 の `左足首` であって、見た目を動かす `左足首D` ではなかった。
武田さんの指摘のほうが正しい。

**修正**。`tools/fix_motion_blend.py` を新規に作り、`mmd_additional_rotation` と
`mmd_tools_at_dummy` の 48 件だけミュートを解除する。IK 系 10 件
（`IK` / `mmd_ik_limit_override` / `mmd_ik_target_override`）は **ミュートのまま残す**
（脚は FK 回転で駆動しており、キーの無い `足ＩＫ` が効くと足が引き戻されるため）。

**効果（実測、単位 cm・全コマ中の最大移動距離）**:

| ボーン | 修正前 | 修正後 |
|---|---|---|
| 左ひざD | 14.67（腰と一緒の棒振り） | 3.39（`左ひざ` と完全一致＝曲がっている） |
| 左足首D | 20.68（同上） | 11.37（`左足首` と完全一致） |
| 右ひざD | 15.47 | 3.86 |
| 右足首D | 21.41 | 12.15 |

修正後は D ボーンの移動量がアニメーション側のボーンと小数点まで一致する。
これが付与親が正しく効いている証拠。

### 不具合: 再生範囲が 0–403 コマ

同 blend に入っていた 2本目のクリップ（404コマ）に合わせて `scene.frame_end` が
設定されていた（`helen-retarget-game-motion.py` が全クリップの最大値を使う）。
敬礼は 191コマなので、再生すると後半 200コマ以上が無変化だった。修正済み。

### 不具合: 揺れものが焼かれていなかった／剛体ワールドが無効

`scene.rigidbody_world.enabled = False` のままで、コートも髪も完全に硬直していた。
さらに私は下見用動画を `--physics-off` で描いていたため、武田さんに見せた画像は
**揺れが最初から入っていない絵**だった。

**修正**。先頭に **助走 60コマ**（1秒）を入れて最初のポーズを保持し、そこで布と髪を
落ち着かせてから動き出す形にした（Action のキーを +60 ずらし、剛体キャッシュは 0–250、
再生範囲は 60–250）。焼き込み後の実測: 揺れる剛体 224本のうち **動かなかったもの 0本**、
最大 6.25cm、中央値 2.86cm。

## 表情の取り込み（2026-08-04）

武田さんが 52本の下見動画を見て「動きがキモイ」と指摘。顔を拡大して確認したところ、
怒り・喜びの動きでも**顔がまったく変わらない**（まばたきもしない）ことが原因だった。

- 表情データはゲームの AnimationClip の `type_id=137`（SkinnedMeshRenderer）に入っている。
  名前は伏せられ CRC32 の数値になっている。
- ミティールの Mesh から取り出した 24個の名前を `zlib.crc32(名前)` でハッシュ化すると
  **24/24 一致**（`blendShape.<名前>` を付けた形では 0/24。実測で確定）。
- ゲームの 24個 → MMD の表情への対応表は `tools/add_face_animation.py` の `MAPPING`。
  同じ MMD 表情へ複数来る場合は各コマで最大値を採る。値は 0〜100 → 0〜1 へ換算。
- 生成物は `<動き名>_face` という別 Action。`batch_bake_render.py` が体の動きと一緒に載せる。
- 52本中 50本に表情が入った（残り 2本は元データに表情が無い）。

**途中で踏んだ失敗（同じ轍を踏まないこと）**

1. 「ずっと同じ値のカーブ」を"動いていないから不要"として捨てた → 表情の土台（笑った口・
   閉じ気味の目）がまるごと抜け、眉だけ 3% 動く実質無表情になった。**値が 0 のものだけ落とす**。
2. `constant` 形式のカーブ（`samples` を持たない持ち方）を読めず `KeyError` で落ちた。
3. `_face` Action を体の動きと誤認して動画にし、本数が 28→56 に倍増した。

### 真の原因（2026-08-04 実測で確定）

**位置カーブは元データに存在する。** `mityl-lobby.json.gz` / `mityl-control.json.gz` の
Unity binding `type_id=4, attribute=1`（Transform Position）に、`root/Root_M` を含む
360本の位置カーブが全フレーム分入っている（28本すべてで確認、最大振幅 40cm＝`Cafe_Enter`）。

浮きの原因は **`helen-retarget-game-motion.py` が腰の移動を「フレーム0からの相対値」で
載せていたこと**（同スクリプト 266–279行）。

```python
first_root_position = first_global[root_index].translation.copy()   # frame 0 を原点にする
root_offset = (animated_global[root_index].translation - first_root_position) * scale_ratio
```

ゲームのクリップは、**クリップ開始時点ですでに腰が落ちている**。素の姿勢（rest）の
Root_M ローカル高さ 1.0324 に対し、frame 0 の高さは:

| 動作 | frame 0 の腰高 | 素の姿勢との差 |
|---|---|---|
| 立ち系（Idle / 感情系）| 0.865 前後 | **−17cm** |
| 寝そべり `Lie_0_Loop` | 0.640 | **−39cm** |
| 座り `Sit_0_Loop` | 0.605 | **−43cm** |
| 膝立ち `Kneel_0_Loop` | 0.106 | **−93cm** |
| `Special_0_Clip` / `_Loop` | 0.083 | **−95cm** |

frame 0 を原点にすると、この **開始時点の落ち込みが全部 0 に潰れる**。結果、膝立ちや
座りは脚だけ折り畳まれて腰が立ち姿の高さに残り、体ごと宙に浮いた。クリップ途中で腰高が
大きく変わる `Kneel_0_Start` / `_End` は、1つの定数では追随できず最悪の 74cm になった。

**正しい実装**は、原点を frame 0 ではなく **素の姿勢（`rest_global[root_index]`）** に取ること。
これで開始時の落ち込みも途中の上下も、ゲームのカーブどおりに再現される。

**`fix_ground_contact.py` は撤去する。** 誤った原因診断に対する対症療法であり、
クリップごとの定数上下移動という第2の近似を重ねて、動きの人間らしさを失わせていた。

対処として `tools/fix_ground_contact.py` を適用した。クリップごとに「いちばん低くなる瞬間が地面に着く」
1つの値だけ `全ての親` へ入れる。1コマごとに動かすと走りの跳ねが消えるため、あえて
クリップ単位。**適用後は 52本すべて地面からのずれ 2cm 以内**。ただしこれはメッシュ最下点を
使った内部指標であり、正しい腰高・足運び・接触順序・原作動作との一致は証明しない。

**踏んだ失敗（同じ轍を踏まないこと）**

1. 接地の基準を「足首」にした → 膝立ちは膝が接地点なので体が持ち上がり悪化。
   **メッシュのいちばん低い点**を基準にすべき。
2. `全ての親` は骨の Y が世界の上を向いている。世界の Z をそのまま `location` へ
   入れると横へ動く（実測で確認）。
3. **キーを消してもポーズ骨に入っている値は残る**。ループで次のクリップを測る前に
   `location = (0,0,0)` へ戻さないと、前のクリップの補正が持ち越されて測定値が全部壊れる。
   これに気づかず 3回作り直した。
4. fcurve を足した直後は評価に反映されない。アクションを付け直す必要がある。

### 分かったこと: 載せ替えは失敗していない（※上記のとおり取り消し）

棒人間（ゲームのデータそのもの）と MMD 出力を同じ床・同じカメラで並べると、**4本とも
ほぼ同じ動き**をする。骨ごとの位置差も、素の姿勢の時点で既に存在する体型差が主因だった。

| `Run_0_End_L` | 77.0cm | **0.1cm** | 13.9cm | 7.1cm |
| `Run_0_End_R` | 80.1cm | **0.1cm** | 14.4cm | 8.1cm |

合否の基準を「0cm」ではなく **原作が持っている自然な足の転がり量**に置いた。
原作側の値は `tools/game_foot_trajectory.py` がゲームデータから順運動学で直接測ったもので、
MMD の出力とは独立している。

### 前提が3つ間違っていた（前回失敗した理由）

1. **接地中の足は止まっていない。** ゲーム側でも毎コマ1.5cm後ろへ下がる（その場足踏み）。
2. **接地区間を MMD の足の高さで判定してはいけない。** MMD はつま先が −4.5〜+9cm しか
   動かず接地と遊脚を区別できない。ゲーム側は 2.6〜14.3cm で4倍以上の差がある。
3. **前進量も MMD 側から作ってはいけない。** ゲーム側の足で作ると体の道筋は横ぶれ1cm以内の
   直線、MMD 側の足で作ると **横へ43cm蛇行**した（載せ替え誤差が体の動きへ化ける）。

さらに前進を正しく入れても滑りが115cm残った。原因は **MMD の足がゲームより1.5倍大きく
振れている**こと（1コマ 2.3cm 対 1.55cm）。回転だけを移す方式では消せないので、
足ＩＫで足首の位置そのものをゲームに合わせた。

### やっていること（`tools/foot_ik_lock.py`）

1. ゲーム側の足から前進を作り `全ての親` へ入れる（歩き89.5cm・秒速0.72m／走り89.8cm・秒速1.22m）。
   接地判定は**つま先の高さ**、進む量は**足首**で測る（つま先は転がるので15cm水増しになる）。
2. ひざの IK 拘束だけ有効にする。
3. `左足ＩＫ`/`右足ＩＫ` をゲームの足首位置（縮尺換算＋前進ぶん）へコマごとに置く。

床からのずれは −3.14〜+1.95cm で、足ＩＫ無し（−3.65〜+5.82cm）より床に近い。

### 試して捨てたもの

- **つま先ＩＫも使う** → つま先の滑りが 32.3→33.4cm、走りは 59.7→69.1cm と**悪化**。不採用。
- **MMD 側の足で接地固定** → 滑りは0になるが体が横へ43cm蛇行。不採用。
- **片足支持から等速を見積もる** → 99.6→90.8cm しか減らず不採用。

### 残っている差

つま先の転がりが原作の約1.8倍。足首の角度（載せ替えの回転）が原作より大きいため。
直すには足首の回転もゲーム側から作り直す必要がある（未実装）。

**成果物**: `02_blend/Mityl_歩行走行4本_足IK.blend`、`03_preview/歩行走行4本_足IK/*.mp4`、
`03_preview/足滑り比較.html`

## 8. 監査がゆがみを見逃した原因の特定（2026-08-05・調査のみ、実装は保留）

武田さんが `Lobby_MitylSSR0101_Lie_0_Loop`（寝そべり繰り返し）の動きのゆがみを目視で指摘した。
全件監査を通っていたクリップなので、**監査側の欠陥**として原因を調べた。
設計案の正本は `gf2-mityl-motion/reports/欠陥検知の設計-20260805.md`。

### 原因

現行の全件監査（`tools/audit_output.py` → `run_all_52.sh` 関所5）が測っているのは3つだけ。
①メッシュ最低点（床へのめり込み）②接地した足の水平移動 ③腰の水平移動。

`Lie_0_Loop` の実測は 最低点 **+14.8cm**／滑り4か所とも 0.0cm／腰の移動 0.0cm で、**3指標すべて満点**。
寝そべりは足が接地判定に入らず体も移動しないため、この3指標に**構造的に引っかからない**。

さらに次の2点は、追加計算なしで拾えたのに拾っていなかった。

- **判定を「マイナス（沈む）だけ異常」に固定していた。** +14.8cm は「寝ているのに床から15cm浮いている」
  という欠陥そのもの。52本中、床から3cm以上浮いているのは `Lie_0_Loop`(14.8) と
  `Angry_0_Loop`(3.5) の2本だけで、突出した外れ値だった。
- **同名クリップを突き合わせていなかった。** `Control_MitylSSR0101_Lie_0_Loop` は −12.7cm。
  同じ寝そべり動作で27cm食い違う。

**最大の原因は工程側。** 原作の骨と1コマずつ比べる `tools/diff_against_game.py` は 2026-08-04 に
作ってあったが、**量産の関所に接続しなかった**（`grep diff_against_game tools/run_all_52.sh` は0件、
適用実績は `reports/diff-against-game.json` の4本・21骨のみ）。道具の不在ではない。

### ヘレン案件との工程差（体験差の正体）

| | ヘレン（v2.1 / 休憩室 v2.2） | ミティール |
|---|---|---|
| 完成基準 | 途中で明示的に引き下げ、原作胸機構の再現を捨てると明文化 | 「原作再現」のまま、原作を見ずに進行 |
| パイロット単位 | H0157 **1件**の承認後に残り33件へ展開 | 代表4本→**51本を一気に** |
| 閲覧手段 | Motion Browser + Blender で本人が Action 切替 | mp4 52本を1カメラ角で並べただけ |
| 検査道具 | 40本（形状・剛体貫通・メッシュ交差・妥当性・連続性・カーブの飛び） | 27本（床・滑り・腰の3指標） |
| しきい値 | **武田さんの承認/却下からファイルへ較正**（`inputs/plausibility-gates.json`） | LLM が決めた |

**決定的なのは最後の行。** ヘレンでは武田さんの「これはダメ」がそのままファイル上のしきい値になり、
次の実行で自動的に引っかかる（`plausibility-gates.json` は承認3件と却下1件の間から数値を導出し、
「外套が5度/コマを超え続けた最長34コマ、frame 655 から」が武田さんの目視指摘
「650〜680フレーム付近」と同じ場所を指した）。ミティールでは判断が会話に残っただけで、
機械に翻訳されなかった。

### 再利用できる資産（ヘレン案件に既存）

ミティールで一から作りかけた検査は、ヘレン側に既にある。次回は先に読む。

- `motion_plausibility.py` — 動きとしてありえるか（減衰・末端が根元より速く回っていないか）
- `validate_mesh_penetration.py` — メッシュ面の実交差。**静止姿勢の交差を引き算**する点が要
- `repair_curve_pops.py` — 抽出のドロップアウト（1〜2コマだけ跳ねて戻る）の検出
- `inputs/plausibility-gates.json` — しきい値の較正方式（承認/却下の差が2倍未満の指標はゲートにしない）

場所: `gf2-helen-starlit-waltz/05_helen-motion-library/library-v2-fidelity/rest-room-v2.2/tools/`

### 出来を測る指標の標準セット（外部調査・2026-08-05）

リターゲットの評価指標は学術的に標準セットが確立している。
**足の滑り / 地面へのめり込み / 浮き(foot clearance・floating) / 自己交差 / なめらかさ(jerk)** の5つ。

本件の監査はこのうち2つ半（滑り・めり込み・浮きの片側だけ）しか持っていなかった。
**「浮き」は標準指標であり、独自に思いつく必要のあるものではなかった。**
先に標準セットを調べていれば `Lie_0_Loop` は初回で落ちていた。

ただし文献側も「自動指標と人の知覚の一致は未解決」と明記している。目視の回数は減らせるが、ゼロにはできない。

### ドルフロ2 → MMD 固有部分の前例

検索範囲では**前例が見つからなかった**。公式MMDモデルの配布キャラ一覧の記事はあるが、
ゲーム内モーションを抽出して公式MMDへ載せる手順の記事は見当たらない。
一方、抽出（AssetRipper）・Blender へのリターゲット（公式拡張 `Retarget` に MMD プリセットあり）・
MMD 側の扱い（`mmd_tools`）はいずれも確立済み。
CRC32 パスハッシュの骨名解決 / 座標変換 / 付与親・足ＩＫ・剛体追従の扱い / その場足踏みへの前進付与は
自作が妥当だったと判断する。
