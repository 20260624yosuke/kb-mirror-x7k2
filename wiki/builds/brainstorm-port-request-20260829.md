## ここから下をそのままコピーして貼る

あなたの環境に `/brainstorm` 相当のスキルを実装してください。
Claude Code では既に動いており、同じ使用感をこの環境でも出したい、という依頼です。
**実現方法はあなたが決めてください。** 下は満たしてほしい条件で、作り方の指定ではありません。

### このスキルは何か

私（武田）はアイデアを出す人で、あなたはそれが成果物につながるよう導線を敷く人です。
その導線を敷く作業（＝計画作成）までをこのスキルで行い、**実装はしません**。

作った理由は、計画をプランモードで作ると**やり取りがファイルに残らず**、コンテキストの
自動圧縮で私の考えが消えて、また同じ方針を伝え直すループになるからです。
このスキルは普通のモードで動き、**話しながらメモをファイルに書き足します。メモが消えないことが本体です。**

### 満たしてほしい条件（11項目）

1. **会話を勝手に閉じない。** 私が承認または中断を明示するまで、あなたの応答は必ず承認の選択肢
   （その環境で選択肢を出す仕組み。Codex なら `request_user_input`）で終わること。
   指摘・質問・「わからない」・沈黙・選択肢を閉じただけ — 全部「話の途中」です。
   答えたうえで、**同じ応答の中で選択肢を出し直す**こと。
   承認とみなす言葉:「承認」「任せます」「それでいい」「進めて」「やって」「OK」「了解」「問題ない」。
   中断とみなす言葉:「やめる」「中断」「中止」「いらない」「取り下げ」。曖昧なら承認扱いにしないこと。

2. **選択肢には毎回「それを選ぶと失うもの」を書く。** 代償の見えない二択は選ばせたことになりません。

3. **話した内容を毎ターン、メモへ書き足す。** 私が考えを述べたら、その回のうちに私自身の言葉で
   書き足すこと。**要約して薄めないこと。** 会話の中で設計を育てず、ファイルへ落とすこと。

4. **実装しない。** コード・ツール・設定など成果物への書き込みは、その環境の仕組み（フック等）で
   **機械的に止める**こと。メモ・`wiki/` 配下・台帳・一時ファイルは書けてよい。
   **計画を .md に書くのは実装ではありません。**

5. **矛盾を見つけたら、承認を取らずに直してよい。** 判定は1問だけ:
   「この編集で、私が後で見る成果物の中身・見え方・使い勝手が変わるか？」
   変わらないなら黙って直して `## 直した記録` に1行残し、その場では報告しない
   （選択肢を出すときに件数だけ添える）。変わるなら直さず聞くこと。
   私は承認を取られ続けると認知負荷でプロジェクトの本筋を見失うので、ここは自律してください。

6. **コンテキスト圧縮でメモの内容が消えないようにする。** その環境に圧縮前後で走る仕組みがあれば、
   メモの要点を毎ターン／圧縮時に文脈へ戻すこと。無ければ代替手段を考えること。

7. **文言ルールだけに頼らない。** 上を機械（フック・スクリプト）で担保すること。
   ルールはコンテキストが膨らむと忘れられるからです。
   **どんな失敗でも「素通り（作業を止めない）」に倒すこと。** 監査が壊れて作業できなくなる事故を
   作らないでください。

8. **メモの書式（機械が読む部分）は、勝手に変えないでください。** 判定の仕組み・フックの組み方は
   自由ですが、次はそのまま使ってください。**別の LLM が書いたメモを読めなくなるからです。**

   ファイル冒頭（frontmatter）:

   ```yaml
   ---
   type: analysis
   status: active
   confidence: medium
   evidence_level: user-stated
   last_reviewed: YYYY-MM-DD
   brainstorm_status: active   # active（議論中）→ ready（実装してよい）→ done（消化済み）
   scope:
     - /絶対パス/このメモが縛るフォルダ
   entry_paths:
     - /絶対パス/再開時に必ず読むファイル
   background_paths:
     - /絶対パス/背景資料
   ---
   ```

   節の見出し（この名前で固定）:
   `## 武田さんの考え` / `## 決まったこと` / `## まだ決まってないこと` / `## 捨てた案と理由` /
   `## 直した記録` / `## 再開の入口（実パス）` / `## 実装への申し送り` / `## 関連リンク`

   `scope` / `entry_paths` / `background_paths` は **インデント付きの `  - /絶対パス`** で書き、
   `*` などの穴埋め記号は使わないこと（実在を確かめられないため）。
   `scope` を書き忘れると無関係な作業まで止まります。`done` に下げ忘れると実装が拒否され続けます。

9. **メモは階層フォルダに置きます。探索は再帰で実装してください。**

   ```
   wiki/analyses/brainstorm/<プロジェクト>/
       _index.md                      ← 親1枚。計画と引き継ぎの正本。子と関連ファイルを実パスで束ねる
       20260829-<セッションの主題>.md   ← 子。セッションごとに1枚
   ```

   **機械が読むのは親1枚**で、子は親から辿ります。親と子を二重に数えないこと。
   2026-08-29 時点では移行前で、`wiki/analyses/brainstorm-<テーマ>.md` に平置きされています。
   **どちらも見つかるように書いてください。**

10. **渡した先から辿れる形にする。** `[[slug]]` は Obsidian の記法で、新しいセッションの LLM は
    解決できません。`[[slug]]` を書いたら、同じファイルに `wiki/analyses/<slug>.md` のように
    **フォルダを含む実パス**を必ず併記すること（裸のファイル名は不可）。
    `## 再開の入口（実パス）` には、渡された人が最初に読むものを実パスで書くこと。
    これも機械で検査してください（`ready` へ上げるとき／引き継ぎのまま会話を閉じるとき）。
    実際に、計画書を渡したのに関連ファイルへ辿れず、私の指摘が唯一の検出手段だった事故があります。

11. **パスに半角スペースが入っていることを前提にする。** 知識ベースのルートは

    `/Volumes/SSD_M.2_Realtek RTL9210 NVME Media_/05_claude/claude_llm_wiki/LLM Knowledge Base _01`

    で、半角スペースが2つあります。**コマンド文字列を空白で切ってパスを取り出す実装は必ず壊れます。**
    Claude 側で実際にこの誤検知が出ました（1つ目のスペースで切れた、存在しない断片で書き込みを拒否）。
    長い候補から順に実在を試す方式にしてください。

12. **同時起動での上書きに注意。** メモは知識ベースの中に1枚しかなく、複数の LLM が同じファイルを
    読み書きします。書く直前に読み直し、小さな追記で書くこと。全文の書き直しは避けること。

### 揃えるもの・揃えなくてよいもの

- **揃えるのはメモだけです。** スキル本体（規則の文書・フック登録・判定スクリプト）は
  この環境専用で構いません。他の LLM のフォルダを参照する必要はありません。
- 判定の実装方法・フックの組み方・スクリプトの構造は、この環境の作法に合わせて自由に決めてください。
