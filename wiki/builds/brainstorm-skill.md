# brainstorm スキル（会話を切らずに考えを詰める・計画作成まで）

`/brainstorm` の正本。2026-08-28 に [[hold]] スキルを一本化して置き換えた。

## 現在の統合見解

### 何を解く道具か

武田さんはアイデアを出す人、LLM はそのアイデアが成果物につながるよう導線を敷く人。
**その導線を敷く作業が「計画」であり、このスキルは計画作成までを担当する。実装はしない。**

これまで計画作成はプランモードで行っていたが、プランモードには2つの制約があった。

1. やり取りをファイルに残せない（編集ができない）
2. そのためコンテキストの自動圧縮で武田さんの考えが消え、同じ方針を伝え直すループが起きる

brainstorm は普通のモードで動き、**話しながら KB のメモへ書き足す**。メモが消えないことが本体。
あわせて、承認が出るまで会話を閉じない（推論が返る一手前で武田さんが指摘を入れられる）。

### 構成

| ファイル | 役割 |
|---|---|
| `~/.claude/skills/brainstorm/SKILL.md` | 規則本体。frontmatter で PreToolUse（封鎖）と Stop（閉じない）を登録 |
| `~/.claude/skills/brainstorm/brainstorm_guard.py` | 監査スクリプト。6サブコマンド |
| `~/.claude/settings.json` | 常駐分（再注入2本 + 未読ブロック1本）を登録 |
| `wiki/analyses/brainstorm-<テーマ>.md` | メモ本体。1テーマ1枚、日付なし |
| `~/.claude/skills/brainstorm/guard.log` | 監査の動作記録（効いているかを後から数えるため） |

### 監査スクリプトの4つの働き

| サブコマンド | 起動点 | 働き |
|---|---|---|
| `inject-light` | UserPromptSubmit（毎ターン） | メモの要点を context へ戻す（60行/2000字上限） |
| `inject-full` | SessionStart（`compact` 含む） | メモを厚く戻す（240行/8000字上限） |
| `guard-write --lockdown` | PreToolUse（スキル起動中） | 成果物フォルダへの書き込みを拒否 |
| `guard-write --unread` | PreToolUse（常駐） | `ready` のメモを読まずに実装しようとしたら拒否 |
| `guard-stop` | Stop（スキル起動中） | 承認カード無しで会話を閉じようとしたら止める |
| `bypass <session_id>` | 手動 | 武田さんが「解除」と言ったときだけ。その会話の間（24時間）拒否を止める |
| `check` | 手動 | フックの無い環境用。読むべきメモを表示、`ready` が未読なら終了コード1 |

どんな失敗でも素通り（作業を止めない）に倒す。監査が壊れて作業不能になる事故は作らない。

### メモの目印（機械が読む2行）

```yaml
brainstorm_status: active   # active（議論中）→ ready（実装してよい）→ done（消化済み）
scope:
  - /絶対パス/このメモが縛るフォルダ
```

`brainstorm_status` が状態、`scope` が適用範囲。**`scope` を書き忘れると無関係な作業まで止まる。**
`done` に下げ忘れると、そのフォルダでの実装が拒否され続ける（`bypass` で逃がせる）。

### 編集の境界（1問テスト）

> この編集で、武田さんが後で見る成果物の中身・見え方・使い勝手が変わるか？

- 変わらない（記録を実ファイル・実環境に合わせるだけ）→ 黙って直し、メモの `## 直した記録` に1行。
  その場では報告せず、カードを出すときに件数だけ添える。
- 変わる（新しい判断・設計・機能・評価が入る）→ 直さず、カードで聞く。

意味の判断はフックにはできないので、フックは**パスで**引く。`wiki/`・台帳・一時ファイルは書ける、
それ以外の成果物は止める。矛盾修正はほぼ wiki 内なので臨機応変さは死なない。

## 根拠

### 実測で確認したこと（2026-08-28）

- **危険モード（bypassPermissions）でも PreToolUse の deny は効く。** 一時フックを仕掛けて実測。
  Bash のリダイレクト書き込みも Write ツールも拒否され、無関係な書き込みは素通りした。
  フック入力の `permission_mode` は `bypassPermissions` と記録された。
- **フック設定の変更は再起動なしで反映される**（公式ドキュメント: ファイル監視で拾われる）。
- 監査スクリプトの自動試験 **22件すべて合格**（封鎖7・未読5・解除2・再注入3・停止4・異常入力1）。

### 公式ドキュメントで確認した仕様（2026-08-28、Claude Code v2.1.228）

- `PostCompact` は**出力が無視される**ため、context への再注入には使えない。使えるのは
  `UserPromptSubmit`（毎回・確実）と `SessionStart`（matcher に `compact` あり）。
- **スキルの frontmatter に書いたフックは、一度起動したらそのセッションの残り全部で発火し続ける**
  （`once: true` を付けた場合のみ初回で外れる）。よって封鎖はブレストした会話の最後まで残る。
  実装は別の会話で行う設計にしてこれを利用している。
- `Stop` の時点で transcript に最終発話が入っている保証はなく、入力の `last_assistant_message`
  を使うべき。**旧 [[hold]] の `hold_guard.py` は transcript を読んでいた**（移植時に修正済み）。
- Stop フックの連続ブロックは8回で強制的に打ち切られる。

## 矛盾・未確定

- **自動圧縮の直後に `SessionStart` が実際に発火するか未検証。** ドキュメント上は `compact` =
  「自動・手動どちらの圧縮も対象」。空振りしても `inject-light`（毎ターン）で目的は達成される。
- **「メモを読んだか」の判定には取りこぼしがある。** `@ファイル名` での参照とサブエージェント経由の
  読み込みは主の会話ログにツール呼び出しが残らない。倒れる方向は安全側（読んだのに止まる）で、
  `bypass` で逃がせる。
- **Bash コマンドの解析は完全ではない。** 書き込み記号の近似判定なので、すり抜けも誤検知も残る。
- 旧 [[hold]] の `misses.md` が空のままだった理由は未確定。上記の transcript 依存が原因の可能性がある。

## Codex / Kimi へ渡す指示書

武田さんが各 LLM に個別で組ませるための説明。**実現方法はその環境の担当 LLM に考えさせる。**

> ### 依頼: `/brainstorm` 相当のスキルを、この環境で実現してください
>
> **目的**: 私（武田）はアイデアを出す人で、あなたはそれが成果物につながるよう導線を敷く人です。
> その導線を敷く作業（＝計画作成）までをこのスキルで行い、実装はしません。
>
> **満たしてほしい条件**
>
> 1. **会話を勝手に閉じない。** 私が承認または中断を明示するまで、あなたの応答は必ず承認の選択肢
>    （その環境で選択肢を出す仕組み。Codex なら `request_user_input`）で終わること。指摘・質問・
>    「わからない」・沈黙は承認ではない。答えたうえで同じ応答の中で選択肢を出し直すこと。
>    選択肢には毎回「それを選ぶと失うもの」を書くこと。
> 2. **話した内容を毎ターン、KB のメモへ書き足す。** 場所は
>    `wiki/analyses/brainstorm-<テーマ>.md`（1テーマ1枚・日付なし）。節は
>    `## 武田さんの考え` `## 決まったこと` `## まだ決まってないこと` `## 捨てた案と理由`
>    `## 直した記録` `## 実装への申し送り`。私の言葉を要約して薄めないこと。
>    frontmatter に `brainstorm_status`（active / ready / done）と `scope`（縛るフォルダの絶対パス）
>    を必ず持たせること。この2行を機械が読む。
> 3. **実装しない。** コード・ツール・設定など成果物への書き込みは、その環境の仕組み（フック等）で
>    機械的に止めること。メモ・`wiki/` 配下・台帳は書けてよい。**計画を .md に書くのは実装ではない。**
> 4. **矛盾を見つけたら、承認を取らずに直してよい。** 判定は「この編集で、私が後で見る成果物の
>    中身・見え方・使い勝手が変わるか」の1問だけ。変わらないなら黙って直して `## 直した記録` に
>    1行残し、その場では報告しない（選択肢を出すときに件数だけ添える）。変わるなら直さず聞く。
> 5. **コンテキスト圧縮でメモの内容が消えないようにする。** その環境に圧縮前後で走る仕組みがあれば、
>    メモの要点を context へ戻すこと。無ければ、毎ターン頭でメモを読み直すなど代替手段を考えること。
> 6. **文言ルールだけに頼らない。** 上を機械（フック・スクリプト）で担保すること。ルールは
>    コンテキストが膨らむと忘れられるため。どんな失敗でも「素通り（作業を止めない）」に倒すこと。
>
> **既にある部品**: `<KBルート>/../..`（Claude 側）に `~/.claude/skills/brainstorm/brainstorm_guard.py`
> があります。フックの無い環境では、作業前に次を実行すれば読むべきメモが分かり、未読なら終了コード1
> が返ります（Python 3 だけで動き、Claude Code に依存しません）:
>
> ```
> python3 ~/.claude/skills/brainstorm/brainstorm_guard.py check
> ```
>
> **Kimi Code へ**: 旧 hold では `~/.agents/skills/hold/hold_guard_kimi.py` を
> `~/.kimi-code/config.toml` の `[[hooks]] event = "Stop"` に登録していました。同じ場所を使えます。
> ただし旧版は会話ログを読んで最終発話を判定しており、その方式は取りこぼす可能性があります。

## 引き継ぎ到達性の監査（2026-08-29 追加）

### なぜ足したか

2026-08-29、brainstorm で作った計画書を新セッションへ渡した際、計画書に関連ファイルの実パスが無く
`[[slug]]` だけが書かれていた。新セッションの LLM は `[[slug]]` を解決できないため、関連ファイルへ
到達できない状態だった。**武田さんの指摘が唯一の検出手段だった。** 実ファイルを読んで確認した原因は
「書き忘れ」ではなく検出器の不在で、次の3点。

1. `brainstorm_guard.py` にメモ・計画書の中身を検査するコマンドが無かった。
2. `guard-write --unread` は `ready` のメモにしか効かず、今回は `active` のままだったので未発火。
3. ひな型に関連ファイルの実パスを書く欄が無く、`## 実装への申し送り` は空欄でも通った。

### 何を検査するか（H1〜H7・すべて機械判定）

| 記号 | 検査 |
|---|---|
| H1 | `[[slug]]` に対応する wiki ページが実在するか |
| H2 | 各 `[[slug]]` に、フォルダを含む実パスが併記されているか（裸のファイル名は不可） |
| H3 | 本文中の相対・絶対パスが実在するか |
| H4 | 相対パスを使うなら作業ディレクトリの絶対パスが本文にあるか |
| H5 | `entry_paths` の KB 内ファイルから、メモへ戻る実パスがあるか |
| H6 | `entry_paths` / `background_paths` が配列として読め、全件実在するか |
| H7 | `## 実装への申し送り` が空でないか |

`entry_paths`（必読）は中身まで監査し、`background_paths`（背景資料）は実在だけ確かめる。
一般方針のページに、特定案件のメモへの逆リンクを強制しないため。

### どこで止まるか

- **発火点①** `brainstorm_status` を `ready` へ上げる編集（`guard-write --unread` の中。
  bypass 判定の直後・lockdown 分岐より前。**昇格の瞬間はまだ `ready` のメモが0件なので、
  `if not memos: return 0` より後ろに置くと永久に発火しない**）。
- **発火点②** 引き継ぎのパスや `[[` を含んだまま会話を閉じようとしたとき
  （新コマンド `guard-stop-handoff`。`~/.claude/settings.json` の `Stop` に登録）。

対象メモは「cwd が scope 内」または「直前の発話で名指しされた」もの。無関係な会話は無音で抜ける。

### 実測で分かっていたこと

- `guard.log` の `guard-stop` 行12行はすべて自己試験の合成入力で、**本番由来は0件**。
  SKILL.md の frontmatter に書いた Stop フックは本番で発火していなかった。だから
  `settings.json` へ登録した。
- KB ルートのパスには半角スペースが2つあり、空白でパスを切る抽出規則は必ず壊れる
  （既存コードの誤爆実例が `guard.log` に残っている）。貪欲一致＋末尾から1語ずつ削る方式にした。

### 検出力の確認

`python3 ~/.claude/skills/brainstorm/brainstorm_guard.py audit-handoff --selftest`。
第1層で H1〜H7 をそれぞれ壊して対応する記号が出ることと、正常ケースで FAIL が出ないことを確認する。
第2層で合成ペイロードを流して発火点①②が実際に deny / block を出すこと、`settings.json` に
登録があることを確認する。**第3層（実機で `guard.log` に本番行が出るか）は自動化できない。**
2026-08-29 時点で第1層・第2層は PASS、第3層は未確認。

### この監査が見ていないもの

- 書かれた内容が正しいかは見ない。到達できることだけを見る。
- 受け取り側では走らない（送り出す側の関所）。
- `stop_hook_active` により **1ターンにつき1回**しか効かない。
- 口頭だけの引き継ぎ、武田さんが自分でパスをコピーする場合は通らない。
- `entry_paths` の網羅性（挙げ忘れ）は分からない。
