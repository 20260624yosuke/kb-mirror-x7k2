## 骨の親: 推定57本 → 51本（2026-08-11）

b27 は「未解決57本の親は原作データに存在しない」と結論し、全部を推定にしていた。
**その結論の土台が誤っていた。**

- 従来の親判定は「親の rest 行列の逆 × 骨の rest 行列」の平行移動が、クリップの
  ローカル平行移動と**絶対値で**一致するかを見ていた。ヘレン本体の骨では正しく働く
  （対照群 186本で総当たり正解率 **97.3%**、最良残差<1e-3 の帯では **208/209 = 99.5%**）。
- ところが未解決57本では1本も一致しなかった。実測すると 413678026 は
  bind の Chest_M からの位置が `[0.00573, 0.13563, 0.10527]`、
  クリップのローカル平行移動が `[0.00006, 0.00136, 0.00105]` で、
  **向きが同じで大きさがちょうど 1/100**。OBS12 の「変種の骨はスケール0.01でたたまれる」と
  同じ倍率であり、**絶対値で検査したこと自体が誤り**だった。
- 直した判定で 6本を原作データから確定した。
  - 厳密一致（残差 4e-6・2位と250倍以上離れて一意）4本 → `Chest_M` 直下の左右2本と、その子2本
  - たたみ一致（向き一致・倍率ちょうど 0.0100）＋ CRC32 パス名一致 2本 →
    `Chest_M/Cloth2_L02` と `Chest_M/Cloth2_R02`（探索全体の偶然一致の期待値 0.097件）
- **手元でどう変わるか**: 初期表示の Flat メッシュで、推定骨が持つウェイトの割合が
  **16.08% → 0.07%** に下がった。b29 前後で同じ頂点を比べると
  **5,525頂点のうち 1,225頂点が動き、最大 57.2mm**（`logs/before-after-shape.json`）。
  General と cloth1_Fight は 0.0mm、Bend は最大 0.9mm。
- 残り51本は確定できなかった。b28 の反復CRC32探索（偶然一致の期待値 0.097）でも名前が出ず、
  幾何一致でも当たらない。ウェイトを持つのは cloth1_Fight(52.5%) / Bend(31.2%) /
  General(12.0%) / Flat(0.07%)。

```

本体   = (_OutlineWidth × 1.3) × 〔ビュー空間で なめらか法線 × 1/1920 動かした投影差〕
```

## きらきら層 — 参照の道をたどって分母を確定した（2026-08-19）

ステップ0-2（過去の「ヘレン自身の材質データが原作側に存在しない」という結論の検証）。
名前で探すのではなく、**原作が持つ参照の道**をたどった。

### OBS-G1 CAB名の作られ方が分かった（`f58`）

バンドルの内部ファイル名 `CAB-<32桁hex>` は、**そのバンドルの `AssetBundle.m_Name` の MD5**。

```
ヘレンのプレハブ: ディスク上のファイル名 60cd095ab659fba5ff2e6403cb0a75a3.bundle
                  m_Name             148471d57635503e10b51416c38df46b.bundle
                  md5(m_Name)      = c028a0ccb6c27cc7857a2b6272bce82a
                  内部ファイル名     = CAB-c028a0ccb6c27cc7857a2b6272bce82a  ← 一致
```

シーンのバンドルだけ作られ方が別（除外）。それ以外は試料の**全件一致**。
`m_Name` はディスク上のファイル名とは**別の名前**で、この区別がこれまで見落とされていた。

### OBS-G2 配信カタログは両方の名前を持っている

Addressables のカタログは、バンドルごとに **ディスク上のファイル名**と **`m_Name` の hash 部分**の
両方を文字列で持つ。したがって手元に無いバンドルについても CAB → カタログ登録の有無 が突合できる。

**対照実験**: 手元のバンドルの `m_Name` がカタログに載っている率 = **100%**（試料の全件）。
この対照を通さない突合は使わない（下記の私の誤り）。

### OBS-G3 欠落45件は「配信されていない」のではなく「落ちていない」

**プレハブが要求して手元に無い CAB 45件は、45件すべて配信カタログに登録されていた。**

- これまでの正本は「未取得」までしか言えなかった（正しい姿勢だった）。今回、
  **配信物として登録されている**ところまで確定した。
- 2026-08-19 の入手試行で差分ゼロだったことと矛盾しない。あの試行は**1回・1経路**（ゲーム内で
  衣装を表示）だけで、「配信されていない」の証明ではないと正本に明記してある。

### 私の誤りと、対照実験で気づいた経緯（記録）

初版は「カタログから `*.bundle` の文字列を集め、その MD5 と欠落 CAB を突合」して
**「45件すべて未登録」**という逆の結論を出した。カタログの `*.bundle` は**ディスク上のファイル名**で、
CAB の元になる `m_Name` とは別の名前空間だった。
気づけたのは**対照実験を先に回したから**（手元にあるバンドル200本で同じ突合をしたら 0/200 だった）。
以後、突合には必ず陽性対照を付ける。

2つの方法（近接規則・記録構造の固定オフセット）を試し、どちらも対照で誤答を出したので不採用。
`ledger/missing-bundle-files.json` に `status: uncertain` として残した。
**OBS-G3 はファイル名の特定に依存しない。**

## 階調表（RampMap）を調べ直した（2026-08-19・ステップ3と、顔が暗い件）

### OBS-R1 RampMap の16行は 4本×4行の帯。row0 を使うのは正しい

`_ramp` の設定は1件につき4本のグラデーションを持つ
（`Ramp_Diffuse` / `Ramp_Specular` / `Ramp_Fresnel` / `Ramp_Additional`）。
原作の画素側シェーダが `_RampMap` を引くときの V は、実測で

行0〜3 / 4〜7 / 8〜11 / 12〜15 の帯の中心にあたる。

**帯の中の4行は完全に同一**（最大差 **0.0**・`scripts/f65_ramp_bands.py`）。
したがって Blender のカラーランプへ **row0**（Diffuse 帯）を入れているのは**正しい**。

| 帯 | V | 対応 | 始 → 中 → 末（例） |
|---|---|---|---|
| 0 | 0.125 | `Ramp_Diffuse` | (0.155,0.137,0.172) → (0.663,0.659,0.721) → (0.907,0.919,0.948) |
| 1 | 0.375 | `Ramp_Specular` | 黒 → 0.929 → 1.0 |
| 2 | 0.625 | `Ramp_Fresnel` | 黒 → 0.964 → 1.0 |
| 3 | 0.875 | `Ramp_Additional` | 黒 → 0.522 → 1.0 |

## 画素クランプを実装した（2026-08-19・武田さん承認「常駐スクリプトで画面に追従」）

原作の輪郭線の太さは

    min(上限 2.5画素×(縦/1080), max(下限 1.2画素, 世界一定の殻の見かけの太さ)) × COLOR0.w

で決まる。画面の画素が要るので、**カメラと解像度が決まった状態でしか値が定まらない**。
ビューポートを自由に回している間は原作に対応する状態が無いので、
いま見えている視点をそのまま「原作でいうカメラ」として扱う。

### 作り

1. 補助オブジェクト2個（`GF_ViewProbe` / `GF_ViewTarget`）が視点の情報を持つ。
   位置＝視点 / スケール＝(k, s, 遠近か否か) / もう1点で視線の向き。
2. ジオメトリノードがそれを読み、頂点ごとに原作の式を計算する。
3. 常駐スクリプト（blend 内テキスト `GF_OutlineViewport.py`）が 0.1秒ごとに 3Dビューの視点を読み、
   **メッシュのローカル座標へ直して**補助オブジェクトへ書き込む。
   書き込むのはこの2個だけで、25個のメッシュには触らない。

### 実測（`scripts/f64_clamp_verify.py`）

カメラ距離を 0.3 / 0.5 / 0.8 / 1.2 / 1.8 / 2.5 / 4.0 / 8.0 m と変えて、殻が画面上で何画素ぶん
外へ出ているかを数えた。

| 距離 | 実測(画素) | クランプ無し | 原作の式 | 差 |
|---|---|---|---|---|
| 0.3〜8.0 m | 1.140 | 0.834 → 0.180 | 1.140 | **0.0000** |

**全距離で原作の式と一致。**式から 0.05画素を超える頂点は **0%**。
（クランプ無しだと距離とともに 0.834 → 0.180 画素へ細っていく。原作は下限で 1.140 に保つ）

### 途中で見つけた私の実装の誤り（2件とも検証で出た）

1. **視点を世界座標で渡していた。**ジオメトリノードはオブジェクトのローカル座標で動くのに、
   世界座標の視点を渡していたため、クランプがまったく効いていなかった
   （このプロジェクトのメッシュは `matrix_world = UNITY_TO_BLEND` で反転を含む）。
2. **下限「1.2画素」を画面上の画素として実装していた。**原作の `normalize` はクリップ空間の
   xyz 3成分で行われ、そのあと xy だけを使うので、**視線と平行に近い法線では下限そのものが
   小さくなる**（68437〜68455行）。画面上の画素として実装すると真横向きの頂点を押し出しすぎる
   （0.05画素を超える頂点が 29.4%）。「画面に乗る割合 q」を入れて **0%** になった。

### 手元でどう変わるか

- 変化画素は 全身 **2.09%**・胸の寄り **4.41%**（`f60`）。
- **寄っても引いても線の太さが画面上で一定に近くなる**（原作と同じ振る舞い）。
- **戻し方**: `python3 scripts/f63_outline_screen_clamp.py --restore`。

### 限界（DEC / 未確認）

- 原作のクランプは clip の x と y に別々に掛かる。ここでは大きさに対する1本のクランプで、
  そのずれは実測 **最大 0.81画素**（`ledger/outline-formula.json` の anisotropy）。
- 倍率に保険の頭打ち `RATIO_MAX = 64` を掛けてある（**原作の規則ではない・DEC**）。
  上記 q を入れたので実測では一度も掛かっていない。
- **常駐スクリプトは blend を開くたびに Blender の実行許可が要る。**許可しない場合は
  補助オブジェクトに最後に書かれた値のまま（＝止まった視点での太さ）になる。絵は壊れない。
- 背景実行のレンダーでは常駐が動かないので、`f28` が描画するカメラの値を書き込むようにした。
  **これを入れる前は、別の視点の太さで描かれていた。**

### きらきら（Glitter）が何をするものか — OBS

出典 `fragment/GFCharForward/0357.msl` 425〜476行・705〜711行。

**「きらきらの絵を、見る角度に応じて左右にずらして2回重ね、両方に写っている粒だけを残す。
その粒の所だけ粗さを下げ金属度を上げ、最後に面の色そのものをその粒の明るさで置き換える（縁ほど強く）」**

- `_GlitterDensity`（1〜200）は UV に掛かる＝**きらきらの絵の繰り返し回数**
- `_GlitterSpeed`（0〜10）は時間ではなく**視線に応じたずらし量**
- **後段は足し算ではなく掛け算による置き換え**（707行 `色 = 色 × glitter`）。
  粒の無い所は色が 0 に落ちる。だから原作でもこれを有効にする材質はごく限られる（19,869件中1件）
- 計算にストッキング固有の処理は無い。`[Header(Stocking)]` は property 一覧の見出しの位置というだけ

> [!warning] 初版の誤りを訂正
> 初版は後段を「色 += glitter × _GlitterRimIntensity」と書いていた。**誤り。**
> 引用範囲を708行からにしていたため、決定的な707行（掛け算による置き換え）を落としていた。
> 2026-08-18 の独立 checker の指摘で発見・訂正。

この計算は「黒地に明るい粒が疎らな RGBA」を前提にしており、ヘレンの gitter 4枚は形が完全に合致する。
ただし **INF**（ヘレン自身の材質が手元に無く、直接の証拠は無い）。

### 輪郭線の色 — OBS

出典 `fragment/GFOutline/0437.msl`（画素側はこの1本・全147行）と `uber_export.txt` の GFOutline 頂点側。

```
頂点側: t = (正規化(POSITION0.xz) ・ 正規化(光の向きをオブジェクト空間へ.xz) + 1) × 0.5
        TEXCOORD1 = lerp(_OutlineShadowColor, _OutlineColor, t) × _OutlineIntensity
画素側: 輪郭線の色 = _BaseMap.rgb × TEXCOORD1 × _FinalTint × _MainLightColor
```

シェーダの**既定値**は `_OutlineColor = _OutlineShadowColor = (0.6,0.6,0.6)` /
`_OutlineIntensity = 1.0`（他キャラ材質1,120件中1,113件が1.0）/ `_FinalTint = (1,1,1,1)`。
既定では光側と影側が同色なので lerp が無効化される。

> [!warning] **【2026-08-19 訂正】この既定値 0.6 は原作では使われていない**
> `f61` の実分布センサスで、`c_<キャラ>_slg_<部位>_uber` 形式の材質 **514件のうち 289件**が
> `_OutlineColor = (0,0,0,1)`（**黒**）だった。既定値の 0.6 は材質側で上書きされている。
> したがって **原作の輪郭線の色は「基本色 × 黒」＝ 黒**であり、「基本色 × 0.6」ではない。
> 成果物は 2026-08-19 に `f57_outline_color_original.py` で黒へ直してある。
> 台帳 `OL-18` ／ `ledger/outline-color-census.json`。

### 1. 新しい門 `f72_negative_claim_gate.py`（証明の無い否定・不能の結論を止める）

台帳（`ledger/fact-ledger.json`）と**この正本の本文**から、否定・不能の語形を機械的に拾う。
強い否定には次の4点、実現不能の主張にはさらに1点を必須にする。欠けたら監査不合格。

1. `searched_scope` / `searched_paths` / `searched_at` / `tool` — どこを・どの道具で・いつ
2. `search_command`（または `search_script`）と `expected_hits` — その場で再実行して件数が合うこと
3. **`positive_control`（陽性対照）** — 同じ道具・同じ探索先で「有るはずのもの」を探し、
   実際に見つかること。**陽性対照が何も見つけなければ、探索方法そのものが成立していない＝不合格**
4. `falsifier` — この結論が誤りなら、どこを見れば分かるか
5. `attempts`（「できない」のときだけ）— どのスクリプトで何を試してどう失敗したか。
   試していないなら「試していない」としか書けない

満たせないときは **言い方を弱める**。「無い」ではなく
「`ledger/foo.json` を検索した範囲では見つからなかった」。探索範囲と具体的な手がかりを
名指しした過去形の観測（hedged）は、証拠一式なしで通る。
門は「証拠の強さ」と「言葉の強さ」が釣り合っているかを検査している。

### この案件で繰り返している失敗の型

- **問いの立て方が違うと、0件が「無い」に見える。**→ 陽性対照を必須にする（`f72` で機械化した）
- **静的な差分で「無い」と出ても、実行時の観測と突き合わせない限り「無い」は確定しない。**
  → 展開走査（圧縮内部点検）と実行時照合を必須にする（`f97` で機械化した）
- **自分の式を両辺に置くと、検証はいつでも 0 になる。**→ 原作か独立実装と比べる（`f75`）
- **シェーダの既定値は「原作の値」ではない。**→ 実際の材質の分布を数える
- **検証器が空だと、誤りに気づけない。**→ 台帳の数字どうしの引き算・`grep -c`・自分の台帳を
  自分の言葉で引く形は、いずれも `f50` が止めるようにした
