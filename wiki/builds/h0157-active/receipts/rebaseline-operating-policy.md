# 未決4論点の推奨案（実装済み・変更可）

判断基準は依頼どおり「既存の安全性を下げない範囲で、運用コストが最小になること」。
4件とも候補に実装済みで、機械試験で挙動を固定してある。方針を変える場合は、
下の「代償」を見てから差し替える。

---

## 論点1 — scanner が候補として拾わない script 変更の審査強度

**推奨: 判定は必ず必要。ただし判定材料は機械が揃え、語彙を分ける。**

差分に出た行は、scanner が writer 候補として拾ったかどうかで2種類に分かれる。

| 種類 | 必要なこと | 今回の実例 |
|---|---|---|
| scanner 候補（`is_scanner_candidate: true`） | 独立レビューが `writer-retained` / `non-writer` を判定 | 0件 |
| 目録のみ（`false`） | 独立レビューが `non-writer` と確認。writer とは記録できない | 3件 |

- **なぜ自動承認にしないか**: 「scanner が拾わなかった」は「writer でない」の証拠ではない。
  パターンの見落としがあり得る。Q0-CR が塞いだ穴を、運用の都合で開け直すことになる。
- **なぜ全件同じ重さにしないか**: 目録のみの行に writer 判定を許すと、レビューの語彙が
  scanner の判定と矛盾しうる。機械側で `non-writer` 以外を拒否している。
- **コスト**: 変更1本につき1判定。今回は3本。273本は据え置き。
- **選ぶと失うもの**: 自動承認にすれば判定の手間は消えるが、パターン外の writer が
  無審査で baseline に入る経路ができる。

**採否の分かれ目**: 独立レビュー役を人が務めるのか機械が務めるのかは未固定。
今回は `bin/independent_diff_review.py` が実バイトを読んで判定している。
人の目を要求したい場合は、この受領証を人が作る運用に置き換えれば足りる（機械側は変更不要）。

## 論点2 — rename を delete+add とするか、同一性を持たせるか

**推奨: バイトが同一のときだけ rename として扱い、判定を引き継ぐ。ただし旧パスを残し、レビューの明示承認を要求する。**

- 同じ SHA なら、中身は既に審査済みのものそのもの。`SHA不変の行だけ継承する` という
  必須条件と矛盾しない。
- 引き継いだ行には `renamed_from` を残し、レビュー受領証の `acknowledged_renames` に
  無い rename は `propose` が拒否する（黙って移動しない）。
- **中身も変わった rename は rename ではない。** 追加＋削除として扱い、新しい判定を要求する
  （試験 `M4_rename_with_edit_is_add_plus_remove`）。
- **コスト**: rename 1件につき1行の承認。ファイル整理のたびに全審査をやり直さずに済む。
- **選ぶと失うもの**: delete+add に統一すれば「移動も必ず読み直す」一貫性は上がるが、
  単なるリネームでも writer 台帳の行を作り直すことになり、整理作業のたびに審査が発生する。

## 論点3 — baseline 更新を1変更ごとにするか、まとめるか

**推奨: まとめてよい（batch）。上限は設けない。**

- 安全性は変わらない。差分が溜まっている間、関所は閉じたままで、
  溜まった全行が例外なく判定対象になる。件数は「一度に出す判定の数」を変えるだけ。
- 件数を機械で隠さないため、`diff` は added / removed / modified / renamed / unchanged の
  件数を必ず表示する。想定より大きい差分は、その場で気づける。
- 差分が空なら `propose` は「作り直す baseline が無い」と言って止まる（空更新で
  来歴の鎖だけ伸ばすのを防ぐ）。
- **コスト**: 昇格1回で済む。1変更ごとだと、変更のたびに9対象のトランザクションが要る。
- **選ぶと失うもの**: まとめると「どの変更がいつ通ったか」の粒度が粗くなる。
  ただし差分報告と review 受領証が rebaseline ごとに production へ保存されるので、
  中身は後から1件単位で辿れる。

## 論点4 — 目録の対象を `.py` 以外へ広げるか

**推奨: 広げる。scripts root 配下の全ファイルを対象にし、機械生成物と編集中の一時ファイルだけ除外する。**

実測した scripts root の構成:

| 種類 | 件数 |
|---|---|
| `.py` | 275 |
| `.py.bak-20260906`（python ソースの控え） | 1 |
| `__pycache__/*.pyc` | 74 |

- 旧規則（`*.py` のみ）だと、python のソースを持つ `.bak` が審査の外に居座る。
  広げると **275 → 276 件**。増えるのは実質この1件だけ。
- 除外は明示列挙にする: `__pycache__/`、`.DS_Store`、`.pyc` / `.pyo` / `.swp` / `.swo` / `.tmp`。
  **「隠しファイルを一律無視」はしない。** 実測したところ現行の `rglob("*.py")` は
  `.hidden.py` も拾っており、一律無視にすると今より安全性が下がる。
- `__pycache__` を除外しないと、script を実行するたびに `.pyc` が変わって関所が誤って止まる。
- **コスト**: +1行。除外規則の1行説明。
- **選ぶと失うもの**: 広げると、scripts root に置いた無関係なファイル（メモ、出力の控え等）も
  審査対象になる。置き場所を scripts root の外にする運用が要る。
  広げなければその手間は無いが、python ソースを別名で置くと審査の外に出る。
