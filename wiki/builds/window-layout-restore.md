# ウィンドウ配置の保存・復元（Raycast ワンアクション）

## 目的

Mac 再起動・Obsidian 再起動・スリープ復帰などで崩れたウィンドウ配置を、保存済みの配置へ
ワンアクションで戻す。yabai（`~/bin/yabai`、v7.1.25、常駐サービス）に依存する。

## 構成

| 役割 | 実体 |
| --- | --- |
| Raycast 入口 | `~/.config/raycast-scripts/restore_after_mac_reboot.sh` ほか |
| 薄いラッパ | `~/bin/restore-after-mac-reboot` / `save-current-window-layout` |
| 本体（統合） | `tools/restore_supported_window_layout.sh` |
| Obsidian 専用 | `tools/restore_obsidian_layout_with_wait.sh` → `tools/obsidian_llm_kb_window_layout.py` |
| 汎用アプリ | `tools/all_window_layout_restore.py` |
| 保存 | `tools/save_current_window_layout.sh` → `tools/all_window_layout_snapshot.py` |
| 全復元（閉じているアプリも起動） | `tools/restore_full_layout.sh` → Raycast「配置を全部復元（閉じているアプリも起動）」 |
| 保存データ | `tools/window-layout-state/latest.json`（Obsidian）/ `all-windows-latest.json`（汎用） |
| 世代バックアップ | `tools/window-layout-state/backups/` |

復元は Obsidian フェーズ → 汎用アプリフェーズの順。汎用フェーズは
`--allow-warnings --allow-missing --allow-extra --skip-unmovable` 付きで呼ばれる。

## 2026-07-27 の修正

### 1. 動かせない窓のせいで常に「失敗」表示になっていた（修正済み）

`all_window_layout_restore.py` は、サイズ変更を受け付けない窓（CLIP STUDIO PAINT の
ナビゲーター等のパレット）を意図的に skip する。しかし **skip した窓を最終判定の
`move_count` に数え続けていた**ため、動かせるものを全部動かし終えても `exit 2` を返し、
Raycast には「対応済みアプリの復元に失敗しました」と出ていた。

skip した window id を集め、最終判定から除外するよう修正。あわせて
`skipped_unmovable_windows: N` と、本当に残った窓を `- unresolved: <title>` として
名前つきで出すようにした。

### 2. アプリが自分で位置を戻す窓（緩和済み）

CLIP STUDIO のランチャー窓（`CLIP STUDIO / MainFrame`）は、復元中に Space をフォーカスした
拍子にアプリ自身が記憶位置へ引き戻す。手動 `yabai -m window 158 --move abs:…` は即成功するのに
復元では戻らない、という挙動だった。

フォーカスが落ち着いた後に **もう 1 巡だけ再適用する retry pass** を追加
（`--retry-passes`、既定 1。リトライ時は動かせない種類の action を落とす）。
これで復元中の判定は通るようになったが、**復元完了後にアプリが再び引き戻すことがある**。
根治はしていない（下記「未確定」）。

### 3. 保存データが崩れた配置を保存していた（ロールバック）

保存の履歴:

| 保存日時（created_at） | 窓数 | display 1 / 2 |
| --- | --- | --- |
| 2026-07-12T21:07 | 30 | 24 / 6 |
| 2026-07-14T20:30 | 35 | 30 / 5 |
| 2026-07-26T11:44 | 35 | 23 / 12 |
| 2026-07-26T22:10 | 57 | 43 / 14 |

`2026-07-14T20:30` の版が 12 日間ずっと正本として残っていた（＝安定していた武田さんの通常配置）。
一方 `2026-07-26T22:10` の版は窓数が 57 に急増し、`Terminal` と `ターミナル`、`Journal` と
`ジャーナル`、`TextEdit` と `テキストエディット` のように **同一アプリが二重に入っている**。
崩れた状態を保存してしまった版と判断した。

対応: 汎用スナップショット `all-windows-latest.json` を `2026-07-14T20:30` 版へ戻した。
Obsidian 側 `latest.json` は 7/14 版に戻すと開いているノートが変わっていて 8 窓中 1 窓しか
一致しなかったため、**7/26 版（現行）のまま**にした。上書き前の版は
`backups/overwritten-*-before-rollback-20260727-184309.json` に退避済み。

ロールバック後の一致率: 一致 12/40 → **18/24**。

## 2026-08-06 の修正

### 1. Obsidian の1窓残りで全体復元が止まる問題（修正済み）

`restore_obsidian_layout_with_wait.sh` は Obsidian 専用復元の後に再照合し、
`move_count` が残ると汎用アプリ復元へ進まない。今回、`knowledge用_inbox / Claude CodeやCodex...`
の1窓が Space 1 に残り、Obsidian だけで停止していた。

`obsidian_llm_kb_window_layout.py` に復元後の再照合と `--retry-passes` を追加し、
未解決の一致窓だけ再適用するようにした。最終的に残る場合は
`post_restore_mismatch` として対象タイトル、現在 Space、目標 Space を出す。

### 2. 左ディスプレイ Space の保存座標が右ディスプレイ座標で残る問題（修正済み）

09:55 保存版で、対象 Space は左ディスプレイ（display 2）なのに保存フレームの `x=1600` が
右ディスプレイ座標のまま残る窓があった。実際に左ディスプレイへ置くと macOS/yabai は
同じ見た目位置を `x=-960` として返すため、保存値をそのまま比較すると永遠に不一致になる。

復元計画作成時に `yabai -m query --displays` のディスプレイ原点を読み、対象 Space の
ディスプレイ座標へフレームを正規化して比較・復元するようにした。保存ファイル自体は書き換えない。

検証: `python3 -m py_compile tools/obsidian_llm_kb_window_layout.py tools/all_window_layout_restore.py tools/window_layout_safety.py`、
`python3 -m unittest tools.tests.test_all_window_layout_restore tools.tests.test_window_layout_safety tools.tests.test_obsidian_llm_kb_window_layout`、
`/bin/bash tools/restore_after_mac_reboot.sh` は成功。Obsidian は `saved=9 current=9 matched=9 move=0`。
汎用アプリ復元も後段まで到達し exit 0。

## 2026-08-07 の修正（保存事故の原因特定と再発防止）

### 1. 何が起きたか

2026-08-07 08:06 の保存が、正しい配置を上書きした。ログで原因まで確定した。

| 時刻 | 出来事 |
| --- | --- |
| 03:42:32 | `Display is turned off`（pmset ログ） |
| 08:06:01 | `Display is turned on` |
| 08:06:33 | 配置の保存が走る（復帰の **32 秒後**） |

スリープ復帰直後は yabai が窓の AX 参照を取り直せていない。この状態で撮った保存は、
窓数だけ揃っていて中身が壊れていた。

| 指標 | 正常（08-06 09:55） | 事故（08-07 08:06） |
| --- | --- | --- |
| AX 参照あり | 47/49 = 96% | 32/47 = **68%** |
| 無題の窓 | 5 = 10% | 21 = **45%** |
| 移動可能 | 38/49 | 23/47 |
| 同一アプリの二重 | なし | **TextEdit / テキストエディット** |
| 定位置から外れたアプリ | なし | **Grok・Eagle・Google Chrome・システム設定** |

`yabai --restart-service` で AX 参照は 27/42 → 41/42、可動 23 → 37、無題 20 → 6 に回復した。
**スリープ復帰後に配置が崩れたら、まず yabai を再起動する。**

### 2. 「マスト配置」の判定方法（勘で選ばない）

どの保存が正しいかは、1 ファイルを見ても分からない。**直近の保存群で、単一窓アプリが
繰り返し置かれている位置（定位置）を集計し、それと一致する版**を正本とする。
2026-08-07 はこの方法で `2026-08-06T09:55` 版を選び、13 アプリ全てが定位置へ戻ることを
実測で確認した。

画面構成は時期によって変わる（ディスプレイ追加・Space 組み替え）ため、定位置の基準は
**直近 6 版だけ**から作る。全期間を混ぜると現行の版が軒並み「いつもと違う」と誤判定される。

### 3. 保存ガードの強化（`window_layout_safety.py`）

従来のガードは **窓数の増減しか見ていなかった** ため、事故の保存は `save_guard: ok` で
通過していた。保存ファイルの中身を測る検査を追加した。

- `has_ax_reference` 率が 85% 未満
- 無題の窓が 25% 超
- 同一アプリが日本語名と英語名で二重に入る

いずれかに当たると保存を止める（従来どおり UI から force で上書き可能）。窓が 10 未満の
ときは割合が暴れるため健全性では判定しない。事故の保存で 3 項目とも検出、正常な保存は
通過することを実データで確認済み。

### 4. 保存一覧の導線（新規）

| 役割 | 実体 |
| --- | --- |
| 一覧・差し戻し本体 | `tools/window_layout_versions.py`（`list` / `restore <番号>`） |
| 選択ダイアログ | `tools/pick_window_layout_version.sh` |
| Raycast 入口 | `~/.config/raycast-scripts/pick_window_layout_version.sh`（「画面配置の保存一覧から戻す」） |
| CLI ラッパ | `~/bin/window-layout-versions` |

各版を `◎ 健全` / `△ 要注意` / `× 壊れている` で判定して並べる。判定基準は
`window_layout_safety.py` から取り込み、保存ガードと同一にしている（二重管理しない）。
`× 壊れている` 版は確認ダイアログを挟まないと戻せない。差し替え前の正本は
`backups/overwritten-<日時>-*.json` へ退避する。

### 5. クリックで壁紙を表示（無効化済み）

「ウィンドウ以外をクリックすると何か起きる」の正体。`com.apple.WindowManager` の
`EnableStandardClickToShowDesktop` が未設定＝ macOS 既定の有効（常に）だったため、
デスクトップの空きをクリックすると全窓が画面外へ退避していた。

`defaults write com.apple.WindowManager EnableStandardClickToShowDesktop -bool false` +
`killall WindowManager` で無効化。適用前後で窓の位置が 1 つも変わらないことを実測確認
（42 窓中 0 窓が移動）。戻すには同じコマンドで `-bool true`。

> [!warning] 未確認
> この設定が保存データの破壊に関与したかは**確認していない**。今回の事故の説明は
> スリープ復帰 32 秒後の保存で足りており、壁紙クリックは別件の使い勝手の問題として
> 無効化した。

  `has_ax_reference` は39、無題は19%、日本語名・英語名の重複は0件だったため、保存データ自体を

  扱う既存方針は維持した。

## 2026-08-17 「復元を押しても窓が1つも動かない」の原因特定と修正

### 症状

武田さん報告「何度も修復したが挙動がおかしい。根本から壊れているなら作り直しも視野」。
実際には、押しても窓が1つも動かない回と、普通に動く回が混ざっていた。

### 原因1: 既知パレットの例外判定が一度も発動していなかった（確定）

`all_window_layout_restore.py` の `is_known_unmovable_window` は、窓名の一覧
（`""` / `カラーサークル` / `カラーヒストリー` / `情報` / `ナビゲーター`）と
`match["title"]` を比べていた。しかし `match["title"]` は `build_plan` が作る
**照合キー単位の見出し**で、実体は `"CLIP STUDIO PAINT / ナビゲーター"` である。
永久に一致しないため、例外扱いは一度も成立しなかった。

実機で確認（2026-08-17、読み取りのみ）:

```
'CLIP STUDIO PAINT / ナビゲーター' | exempt= False
'Claude / Claude'                  | exempt= False
```

`tools/tests/test_all_window_layout_restore.py` の当時の試験は `match` を手書きし
`"title": "ナビゲーター"` という**実在しない形**を渡していたため、試験は合格し続けた。
**試験が不具合を隠していた。**

### 原因2: 1窓の失敗で全窓の復元を中止していた（確定）

原因1で例外が成立しないため `validate_apply_plan` が全体を中止し、
`error: restore refused` → 終了コード2 → **窓は1つも動かない**。

実機での巻き添えの規模（2026-08-17 実測）:

| | 窓数 |
| --- | --- |
| 要移動で、かつ**動かせる**のに巻き添えで止まっていた窓 | 8 |
| 中止の原因になっていた窓 | 5（CSP パレット類4 + Claude 1） |

CSP の窓は **移動はできる。大きさ変更だけができない**。つまり「大きさを戻せない窓が
あるから」という理由だけで、位置を戻せる窓まで全部止めていた。

### 挙動がバラついた理由

CSP のパレットが偶然すでに正しい位置にある回は「要操作なし」となり中止が起きず成功する。
ずれている回は全滅する。これが「直したのに直ったり直らなかったりする」の正体。

### 発症時期（ログ実測）

`restore-runner.log` で `error: restore refused` の初出は **2026-08-14 21:56**
（当該ファイルの更新は同日 17:32/17:39）。以降 8/15・8/16・8/17 はほぼ全て `exit=2`。
2026-08-14 の「根本修正」で入れた厳格化が、そのまま原因になっていた。

### 容疑者から外れたもの（実測で除外）

- **Space の取り違え**: 保存側は Space の UUID で記録しており、2026-08-17 時点で
  保存済み12個すべてが現存・一致。左ディスプレイの Space 番号が 11,12 → 12,13 へ
  ずれていたが、UUID 照合が正しく追随していた。
- **保存データの破損**: 現行正本 `2026-08-06 09:55` 版は健全性判定を通過。

### 修正内容

1. `is_known_unmovable_window` は生の窓名 `window_title` で判定する。
   `build_plan` の match に `window_title`（生の窓名）と `display_label`
   （その窓自身を指す表示名）を追加した。CLIP STUDIO PAINT は全窓を1キーにまとめるため、
   従来の `title` はキャンバス窓でも「ナビゲーター」と表示され、報告としても誤りだった。
2. `triage_actions` を追加し、**窓ごとに実行できる操作だけを残す**。
   大きさを変えられない窓は移動だけ実行する。全操作が不可の窓だけ諦める。
   `--skip-unmovable` を付けない手動実行では従来どおり全体中止（厳格モード）。
3. 終了コードを3段階にした。`restore_supported_window_layout.sh` は 3 を失敗扱いしない。

| 終了コード | 意味 | 画面表示 |
| --- | --- | --- |
| 0 | 全部戻った | 「完了」 |
| 3 | 一部戻った。戻せなかった窓を名前つきで列挙 | 「一部完了（戻せなかった窓があります）」 |
| 2 | 1窓も動かせなかった | 「失敗」 |

既知の CSP パレットが「大きさだけ戻せない」ケースは `_accepted_skip` として
成否判定に影響させない（2026-07-27 の方針を維持）。

4. 試験を `build_plan` が実際に作る形で組み直した。新しい回帰試験が**修正前のコードでは
   落ちる**ことを確認済み（旧判定 `False` / 新判定 `True`）。

### 検証結果（2026-08-17）

- `py_compile` / `bash -n` 成功。復元関連ユニットテスト **26件成功**。
- 修正前後の同一状態での比較: 実行対象 **0窓 → 12窓**。
- 実復元を実行し `applied_windows: 12`、`need_move_or_resize` は 13 → 5 に減少。
  終了コード3（一部完了）で、シェルは 0 を返した。
- 残り5窓は CLIP STUDIO PAINT のキャンバス／パレットと Claude で、いずれも
  **大きさ変更を受け付けない窓**。位置は戻っている。
- **武田さんの実機確認済み（2026-08-17）**: 「戻っている。完了でいい」。
  内部の数値だけでなく、画面上の見た目でも定位置へ戻ったことを確認した。

## 2026-08-25 「アプリが閉じていると全滅・数分固まり」の修正と復元パターン2本化

### 症状と原因（実測）

- 2026-08-25 09:52〜09:58 に押された3回の復元は全て `saved=10 current=0` のまま待機し、
  180〜300秒後に失敗していた。原因は **Obsidian が一度も起動していない状態でボタンを押したこと**
  （当日の Obsidian プロセス活動ゼロ・クラッシュ報告なし・ログイン項目に未登録を実測で確認）。
- 復元フローは (1) Obsidian 専用フェーズ → (2) 汎用アプリフェーズ の順で、(1) の失敗で
  (2) も中止していた（通過ゲート）。アプリを起動する処理はどこにも無く、「開いている窓だけを
  動かす」設計のため、未起動という単純な状態が「数分固まり→エラー→全滅」になっていた。
- 汎用側にも「保存窓>0 かつ照合0件」で即拒否するゲートがあった（対象アプリの窓が
  1つも無い場合も失敗扱い）。

### 修正内容

1. Obsidian フェーズを通過ゲートから報告に降格。未起動なら `pgrep` で秒速判定し、待ちループに
   入らない（従来は `WAIT_SECONDS` 全額待っていた）。失敗しても汎用フェーズは必ず続行。
2. 汎用側は「対象アプリの窓が0個」なら何も動かさず成功扱い。**窓は有るのに照合0件**の拒否は
   2026-08-14 方針どおり維持（AX喪失の保護なので別物）。
3. 多重起動防止ロック（PID 記録、死んだ PID のロックは自動回収）。同朝に複数実行が交差する実害があった。
4. 新入口「全復元」: 閉じている対象アプリを起動してから復元する第2パターン。

### 入口（2パターン）

| パターン | 入口 | 動き |
| --- | --- | --- |
| 通常復元 | 従来どおり Raycast「Mac再起動後の配置復元」ほか | 閉じているアプリは無視して即復元（数秒〜数十秒） |
| 全復元 | Raycast「配置を全部復元（閉じているアプリも起動）」/ `tools/restore_full_layout.sh` | 閉じている対象アプリを起動してから復元 |

- 起動判定・起動は **バンドル ID 基準**（「メール」「ジャーナル」等の日本語表示名はプロセス名と
  一致しないため）。対応表は `restore_full_layout.sh` 内に実測値で記載。
- 罠の記録: osascript の `application id ... is running` は **true/false どちらの答えでも
  終了コード 0** で返る。終了コードで判定すると全アプリが「起動中」に見える（実装時に混入し、
  実機検証で発見して修正した）。出力の答えで判定する。
- 実測: ChatGPT と Codex は同一バンドル (`com.openai.codex`) を指すため起動は1回でよい。
- `RESTORE_LAUNCH_APPS`（カンマ区切りの表示名）で起動対象を絞れる。テスト・部分復元用。
- 一斉起動は 3秒間隔の順次起動（2026-08-07 型の AX 参照喪失を避ける）。1個の起動失敗で全体は止めない。

## 既知の制限

- Obsidian の窓は「開いているノート名」で照合するため、ノートを切り替えた窓は取り残される。
- サイズ変更を受け付けない窓（CSP のパレット類）は位置も戻らない。これは失敗ではなく
  `skipped_unmovable_windows` として報告される。
- 保存時に同一アプリの日本語名・英語名が別アプリとして二重に入ることがある（上記 3）。
- Safari などで `has_ax_reference=false` の窓は、yabai から移動参照を取れないため skip 対象。
  2026-08-06 実行時は Safari 1窓がこの状態で残った。
