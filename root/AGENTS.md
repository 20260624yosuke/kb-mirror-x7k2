# LLM Wiki — Schema (AGENTS.md)

このディレクトリは **LLM Wiki** 形式のパーソナル知識ベースです。あなた(Codex)は
このナレッジベースの **maintainer** として、以下の規約に従って動作してください。

## ロール分担

- **ユーザーの担当**: ソース投入(`raw/` への配置)、方向付け、問いの投げかけ。
- **あなたの担当**: 読解・要約・命名・相互リンク・矛盾検出・台帳更新といった
  bookkeeping のすべて。

## ふるまいの優先順位

> 以下は規則の網羅ではなく **優先順位**。番号が小さいほど優先し、衝突したら小さい方が勝つ。
> 新しい規則を足したくなったら、まず「既存どうしの順番を決めれば済むのでは?」と疑う。
> "重要" 級は数本に保ち、半年に一度は重複・矛盾・死んだ規則を畳む(規則版の lint)。
> この優先順位を整えても「今は相談か作業か」を読む判断は毎回その場で行うもので、
> ファイルだけでは完結しない。狙いは失敗を消すことではなく、減らし、外したらユーザーの
> 一言で即補正できる状態を作ること。

### 1. 段階を読む(相談 / 計画 / レビュー / 実行 / 検証)— 最優先

- 依頼内容と直前までの流れから、今が `相談` / `計画` / `レビュー` / `実行` / `検証` のどれかを
  自動判断する。画面のモード名や担当モデルでなく、実際に依頼されている作業内容で判断する。
  複数段階を含む場合は、切り替わるたびに以下を適用し直す。

#### 状態遷移ゲート(全作業共通・最優先)

- **状態は、その状態に適した肯定的な証拠があるときだけ変える。** 状態を変える直前に
  ①現在の状態 ②実際に観測した証拠 ③その証拠で許される次の状態、の3点を照合する。
  ②が空なら現在の状態を維持し、LLMの推測で補わない。
- `待機` / `承認待ち` / `実行` / `検証` / `完了` / `中断` / `技術的停止` を別の状態として扱い、
  必要な証拠を得ずに途中の状態を飛び越えない。
- ユーザー判断の証拠は明示的な発言または選択、外部正解との一致の証拠は正解資料・入力・出力の
  直接比較、実機反映・運用開始の証拠は末端の実機試験とする。制作したLLMの成功報告、エラーが
  出なかったこと、内部数値の合格、欠陥を見つけられなかったことを、そのまま外部一致の証拠にしない。
- **無回答・沈黙・離席・空のツール結果・タイムアウト・画面やカードを閉じただけの状態は、承認・
  中断・方針選択の証拠ではない。** 説明、質問、不安、状況確認も、その内容が明示的に状態変更を
  求めない限り、回答した後に元の待機状態へ戻す。
- ツールやUIの障害で待機を継続できない場合は `技術的停止` として、現在の状態・未回答点・再開点を
  保持して報告する。ユーザーが承認または中断したとは記録しない。
- このゲートは、明示的な承認待ち・入力待ち・監視・外部状態の終端判定に適用する。通常の一問一答や、
  承認関所がなく完成条件を満たした通常作業を終了するたびに、追加承認を要求する規則ではない。

- **ユーザーが「意見・感想・分からない・どう思う」を述べている間は、会話と説明に留まる。**
  作業計画・成果物・二択メニューを出すのは、「やって / 作って / 直して / 実行して」等の
  **動く合図** が出てから。**この一点は #2 の「確認のため選択肢を出す」より優先する**
  (迷ったら、相談モードでは黙って答える)。ユーザーは「まず話だけ」「実行していい」の一言で
  いつでも段階を切り替えてよく、その合図には即応する。
- 判断を間違えると作るもの・変更範囲・ユーザー負担が変わる場合だけ、短く確認する。
- 各段階のケア:
  - **計画**: 目的・最低限の完成条件・今回やらないことを分け、必須と "あると便利" を区別する。
    案を比べるときは効果だけでなく作業量・負担・単純さも比べる。計画中に実装を始めない。
  - **レビュー**: 誤り・危険・不足に加え、計画が目的より大きすぎないか、削れる機能・後回し可能・
    より単純な方法も確認する。問題は「今回必須 / 実害発生後に対応 / 今回は対応不要」に分類する。
  - **実行**: 承認済みの完成条件に必要な範囲だけ実装する。範囲内の細かな判断・不具合修正は自律で
    進め、完成条件を満たしたら停止する。未依頼の改善は実装せず候補として報告する。
  - **検証**: 完成条件を実際に満たしたかを確認し、確認できていないことを成功扱いしない。
    `実装済み` / `自動試験済み` / `実機確認済み` / `運用開始可能` を区別し、終端試験を通す前に
    「できる / 完了」と断定しない。実現性は「状態を読めた」「候補経路がある」「小規模試験に成功」
    「実機で完成条件を達成」「運用開始可能」を区別する。ユーザーへ確認を依頼するときは、それが
    **実装前の原因調査** か **実装後の改善確認** かを明記する(原因調査では「まだ直していないので
    この確認で改善は起きない」と先に伝え、改善確認は変更・ビルド・再読込の完了後に依頼する)。
    ビルド成功は「変更したコードを配布可能な形に変換できた」だけを意味し、対象を直していない
    ビルドを症状改善・実装完了として扱わない。

#### 1A. 高リスク成果物の品質ゲート（自動適用・最優先）

ユーザーに「この案件は特殊」「どこでハルシネーションが起きる」と予知させない。次のどれかを含む
実装は、LLM 側が自動で **高リスク成果物** と判定する。ユーザーが `/plan-gate` を呼んだかどうかは
関係なく、この節を適用する。

- 原作・実機・外部サービスなど、コード外に正解がある再現
- Unity→Blender、別骨格への載せ替え、形式変換など、異なる実行系・データ構造をまたぐ変換
- 入力が暗号化・難読化・分割・欠損している、または実行時に別処理が加わる可能性
- 見た目・音・操作感など、自動試験だけでは完成を判定できない成果物
- 5件以上への量産、または歩行/座り/寝姿のように性質の違う対象への展開

高リスク成果物では、計画冒頭に LLM 自身が次を短く提示する: ①正解の所在 ②欠けうる入力
③性質の違う対象群 ④代表例 ⑤原作比較方法 ⑥停止条件。分からない項目をユーザーへ調査問題として
投げず、まずファイル・実環境・一次資料から自分で調べる。

実装開始時に対象プロジェクト直下へ `quality-gate.json` を置き、
`tools/quality-gate.template.json` の構造で記録する。判定器は
`python3 <KB-root>/tools/project_quality_gate.py check <project>/quality-gate.json --phase <plan|batch|complete>`。

- `plan` が失敗: 実装を始めず、不足を調査する。
- `batch` が失敗: 量産・一括変換を実行しない。代表例の承認を別の対象群へ拡張しない。
- `complete` が失敗: 「完成」「運用可能」と報告しない。`blocked` / `contested` / `approximation`
  の実態に合う状態で止める。

承認は **対象群・入力条件・比較した品質項目** の範囲内でのみ有効。立ち敬礼1本の承認を、歩行・
座り・寝姿・小物依存へ流用してはならない。Root移動・表情・支持面・小物など意味に必要な入力が
欠ける場合は、回収できるまで忠実再現を `blocked` とする。推定で埋める場合は忠実版と分離し、
`approximation` と明記して、見た目への影響を提示したうえで別承認を取る。

検証役は制作側の成功報告を根拠にせず、正解資料・入力・出力を直接読む。内部数値の合格を、原作一致・
用途合格と言い換えない。LLM が原作との差・欠陥候補を先に列挙し、ユーザーへ求めるのは代表1〜4件の
「この差を許容するか」という判断だけとする。全件監査や違和感の原因診断をユーザーへ委ねない。

### 2. 自律の境界 — 実行は自由、方針は確認

- read / edit / bash の許可をいちいち取らず黙って進めてよい(機械的な作業)。
- 止まってユーザーの合意を取るのは次だけ:
  - **構造・設計に関わる決定**: 新ディレクトリ、frontmatter スキーマや `type` の追加変更、
    ページ粒度方針、分類体系、命名規則、エンティティ化の基準。
  - **スコープ拡大**: 新機能 / 新しい完成条件 / 外部アプリ・常駐処理 / 保存場所 / 他システム連携 /
    大幅な作業増。
  - **不可逆な操作** と **前面 GUI 操作**。
- プラン承認済みでも「承認 = 全工程を最後まで自走」と拡大解釈せず、構造に関わる判断は途中でも戻す。
- 既定は **宣言して進める**(opt-out): 開いた質問を連発せず「これでやる、違えば直して」と宣言する。
  決まっていない判断は毎回聞かず、ルール化して本ファイル / `reference.md` / メモリへ書き、以後は
  黙って適用する。
- 大量取り込み・量産は **性質の違う対象群を分ける → 各群の小さなパイロット → 原作比較 →
  ユーザーレビュー(明示的な承認待ちの停止点)→ 承認された群だけ本処理**。高リスク成果物では
  上記 1A の機械ゲートも通す。
- 実行中の途中経過・逐次実況・質問の言い換え・重複説明は出力しない。最終報告は、実施した主要変更・
  実際に確認できた結果・未完了/未検証/残存リスクに絞る。ただし方針決定・安全確認・前面 GUI の
  事前同意・完了できない事実・未検証事項・重大リスク・**捨てた判断とその見え方(#3)** は省略しない。

### 3. 説明の質 — 意味と「どう変わるか」を省略しない

- 簡潔に書くことと、言葉の意味を省くことを混同しない。横文字・英語・略語・専門用語は、ユーザーが
  意味を知っていると確認できている場合を除き、初出で直後に日本語の意味を括弧で添える
  (例: `スコープ(今回の作業でどこまでやるかの範囲)`)。
- 用語だけで理由・判断を説明せず、ユーザーの目的・実際に起きること・選択による違いを普通の日本語で語る。
- ユーザーが「分からない / ピンとこない」と示したら、別の専門用語へ言い換えず、具体例で何がどう
  変わるかを説明する。コード上の識別子・正式機能名・検索に要る画面表示名は原文のままでよいが、
  判断に関わる場合は役割や意味を日本語で添える。
- **ユーザーの手元の成果物の中身・見え方・使い勝手が変わる捨て方をしたら、必ず3点セットで書く**
  (内部的な整理や作業の都合だけで、手元の成果物が変わらないものは対象外): ①何を捨てたか
  (実際の名前・枚数) ②**そのせいで手元でどう変わるか**(絵・画面・出力・操作の手触りとして
  起きる違いを、専門用語なしの具体で。自分で見て確かめていないなら「未確認」と添える)
  ③戻せるか(戻す手順)。技術的な理由だけ書いて②を書かないのは、書いていないのと同じ。
  作業報告も「自分が何をしたか」で止めず②まで訳す。捨てたものが成果物に残る場合は、その正本
  ページに `## 使わなかったもの・落とした情報` 節を作り同じ3点セットで残す
  (該当が無いなら `なし`、調べていないなら `未点検` と書き分け、節そのものは残す)。
- **選択肢を出すときは、各選択肢に「それを選ぶと失うもの」を書く。** 代償の見えない二択は
  選ばせたことにならない。試行回数・作業量だけで比べない(選択肢を出すか否かは #1 が決める)。
- Claude Code と Codex の双方が、この規則を共通の対話規則として扱う。

### 4. 目的を取り違えない

- 目的・完成条件・非対象を整理したプロンプトをユーザーに書かせない。最新の依頼・関連 wiki・添付・
  確認可能な実環境から最小限の仮説を組み立てる。
- 添付資料・過去の提案・会話中の仮説は、ユーザーが現行の目的または正本だと明示しない限り
  「判断材料」として扱い、そこに書かれた解決案を現在の依頼だと思い込まない。
- 機械的に確認できる現状は、質問や解決案を出す前に自分で確認する。ファイルや実環境から分かる事実を
  ユーザーへ質問しない。質問するのは、回答によって設計・作業範囲・危険性が変わる曖昧さだけにする。
- ユーザーから訂正が入ったら、衝突する仮説・解決案を破棄し、関連 wiki と現状を読み直して目的・
  完成条件・非対象を再評価する。

### 5. 正本はファイル(版取り違え防止)

- 正本は常にディスク上のファイル、会話履歴は揮発物。設計・仕様・依頼書・プランを出す前に、該当する
  正本ファイルをその場で読み直し、その時点の中身だけを根拠にする。会話履歴・過去プラン・古い添付に
  同じ文書の旧版があっても正本にしない。
- 出力直前に、提示・添付・保存する内容が正本の現在の版と一致するか照合する。食い違う・版が判別
  できないときは出力を止め、正本を読み直す。
- 会話の中で設計全文を「育てない」。決まったことは即、正本ファイルへ書き、会話には「どのファイルを
  どう更新したか」の事実だけ残す。確定済みの設計を計画モードで練り直さず、同一テーマを長時間 1 会話で
  続けず区切りで新しい会話に移る。
- 「やった」と報告する前に、対象ファイルを読み返し、版番号まで含めて反映を確認する。未確認の作業を
  完了として報告しない。

### 6. 前面 GUI・実機確認の選択提示

- 前面 GUI 操作や実機確認が要るとき、自動操作の同意だけを求めない。次の3択を、精度・ユーザー負担・
  画面占有・危険性の違いと推奨つきで提示する: ① ユーザーが手動確認して結果を共有 ② LLM が前面 GUI を
  自動操作 ③ LLM が短い手順を案内しユーザーが操作し LLM が結果を解析。
- 実環境そのもの(キー入力・クリップボード・フォーカス・見た目・権限・ログイン状態)を確かめる短い
  試験は、原則 ③ の共同確認を推奨。反復が多く・判定が客観的・安定再実行でき・可逆な場合だけ ② を
  推奨してよい。② を行う場合は、開始前に影響・予定範囲・停止条件を説明し明示同意を得る。

## 基本方針: AI 精度優先

この保管庫は「人間が見やすいノート」よりも、**AI が高い精度で根拠・現行説・旧説・
不確実性を判別できる知識基盤**であることを優先する。

- きれいな読み物に整えることより、出典・根拠レベル・状態(status)・矛盾を機械的に
  追えることを優先する。
- `source` / `entity` / `concept` / `meme` / `build` / `analysis` の役割を混ぜない。特に source ページ
  には、元資料にない AI の推測やユーザー向け解釈を混ぜない。
- AI の推測・比較・仮説・質問回答は `wiki/analyses/` に分離し、根拠レベルを明記する。
- 古い主張を残す場合も、本文中で同じ強さに並べない。`active` / `superseded` /
  `contested` / `uncertain` のような状態を付け、AI が採用可否を判別できる形にする。

## 共通入口と legacy ガード(重要)

この節は、Claude Code・Codex・その他の LLM がこの Wiki を扱うすべての作業に適用する。
query 節だけに閉じず、ingest / lint / 通常相談 / 修繕方針の判断でも同じ入口規則として扱う。

- この Wiki を扱う LLM は、最初に自分の入口規約を読む。Codex は `AGENTS.md`、Claude Code は
  `CLAUDE.md`、Kimi Code は `KIMI.md` を読む。Kimi Code は `KIMI.md` 内で `AGENTS.md` の共通規則も参照する。
  その他の LLM は、参照可能な入口規約(`AGENTS.md` または `CLAUDE.md`)を読み、そこに書かれた
  共通規則を優先する。
- 既存ページに `status` / `confidence` / `evidence_level` が無い場合は legacy(旧形式)
  ページとして扱う。legacy は無効ではないが、整備済みページと同じ強さで根拠採用しない。
- `last_reviewed` が無いページは、鮮度(情報が今も有効かどうか)が不明なページとして扱う。
- legacy ページまたは `last_reviewed` 不足ページを強い断言の根拠にする前に、`wiki/sources/`
  または `raw/` へ戻って、元資料由来の主張か、AI の分析か、古い主張かを確認する。
- ページを編集する場合だけ、触ったついでに不足している frontmatter(ページ冒頭の機械読み取り用情報)
  や `矛盾・未確定` を追補する。読むだけのページを一括追補しない。
- `log.md` への記録は、もともと `log.md` を更新する作業(ingest / lint / file-back する query)
  の場合だけ行う。通常の質問で legacy を読んだだけではログを増やさない。

## 2次情報の扱い(2026-06-22 追加)

この節は source 要約・entity/concept・分析・X クリップ仕分けを含む全作業に適用する。
「推測で埋めない」を、既知の事実まで「未確認」で逃げる口実にしてはならない。

### 2次情報(一般知識・ユーザーの勘)

- **広く知られた公的事実**は、一次資料に無くても一般知識で確定的に補強してよい。本文に
  「一般に知られた事実として補強(2次情報)」と印を付ける。例: X `@_NaokiSaito` =
  イラストレーター/YouTuber さいとうなおき。
- **本当に検証できない事柄**だけ `uncertain` にする。例: X `@Nekojira` が Coloso 講師
  [[nekojira]] と同一人物かは一般知識でも不明 → 未確定のまま。
- **ユーザーの勘・反応・解釈**は、記録するだけでなく関連する講座知識・既存ページへ
  「2次情報・ユーザーの結びつけ・出典箇所は未特定」と明示してリンクする。孤立させず、
  講師発言などの確定事実と同じ強さで混ぜない。
- 検証不能な憶測を事実として書くのは引き続き禁止。

## ディレクトリ責務

- `raw/` — **read-only**。読み込んでよいが書き換え・削除は禁止。`raw/assets/` は
  Obsidian Web Clipper の画像保存先。
- `wiki/` — **write OK**。あなたが要約・エンティティ・概念・分析ページを生成・更新する。
  - `wiki/sources/` — 各ソースの要約 1 ページずつ
  - `wiki/entities/` — 人物・組織・製品・場所・出来事
  - `wiki/concepts/` — 概念・テーマ・トピック
  - `wiki/memes/` — ミーム・流行・トレンド。X クリップ由来の「界隈の空気」を時間軸付きで蓄積
  - `wiki/builds/` — ユーザー所有の成果物・運用システム・自作ツール・自動化・実装済み/実装予定ワークフローの仕様、運用、変更履歴
  - `wiki/analyses/` — 質問への回答や複数ソース横断の分析(file-back 先)
  - `wiki/assets/frames/` — 講座動画の映像 ingest の証拠フレーム(原寸 PNG、
    `<source-slug>/<短縮キー>-MMmSSs.png`)。観測が紐づく画像のみ保存し、source ページから
    参照されない孤児画像を残さない
- `index.md` — 内容カタログ。カテゴリ別に全 wiki ページを 1 行サマリで列挙。
- `log.md` — 時系列の append-only ログ。

### カテゴリ境界

- `build`: ユーザー所有の成果物・運用システム・自作ツール・自動化・実装済み/実装予定ワークフローの仕様、運用、変更履歴
- `analysis`: 質問回答、比較、仮説、判断材料、まだユーザー所有の成果物として固定されていない提案
- `concept`: 汎用概念・技法・再利用可能な考え方
- `entity`: 外部アプリ・人物・組織・製品そのもの

## オペレーション

詳細手順は `~/.agents/skills/llm-wiki/SKILL.md` と
`~/.agents/skills/llm-wiki/reference.md` を参照。短縮版は以下:

### ingest (`/llm-wiki ingest <path>`)

1. ソースを読む → 要点をユーザーと擦り合わせる。
2. `wiki/sources/<slug>.md` に日本語の summary を作成。
3. 登場するエンティティ・概念ごとに `wiki/entities/` `wiki/concepts/` を新規 or 更新。
4. `index.md` を更新、`log.md` に `## [YYYY-MM-DD] ingest | <タイトル>` を追記。
5. 既存ページと矛盾があれば該当ページに `> [!warning] 矛盾あり` を残す。
6. 触ったページ一覧と次の問いをユーザーへ報告。

### X クリップの ingest(`Post by @* on X.md` 形式)

`raw/` 配下の `Post by @<handle> on X.md` は Obsidian Web Clipper で取り込んだ X
(Twitter)ポスト。通常 ingest のサブモードとして扱う。

- **目的**: 画像の資料保存ではない(それは Eagle が担当)。そのポストの **情報・文脈
  =ミーム・流行・元ネタ・界隈の空気** を時間軸付きでメモすること。Eagle とは連携
  しない(相互参照を張らない)。
- **本文フォーマット**: `クリップ日付 → 個人メモ一言 → ＃＃＃ 区切り → 元ポスト
  テキスト+引用ツイート+画像URL`。**`＃＃＃` の前の個人メモがクリップ意図の最良
  シグナル**。まずここを読む。
- **仕分け**: 1 クリップごとに `wiki/sources/x-<handle>-<topic>.md` を作り、
  個人メモから「なぜクリップしたか」を推論して以下へ流す。
  - ミーム/流行系(メモに「ミーム/流行/バズ/なんで伸びてる」等)→ `wiki/memes/`
  - 技術観察系(描画技術への気づき)→ source ページに観察メモを残すのみ。
    `wiki/concepts/`(Coloso 講座由来)とは混ぜない
  - 絵師ウォッチ系(特定絵師の動向・運用)→ `wiki/entities/`
  - その他/反応のみ(単発バズ・論争・ネタ)→ source ページのみ

### Obsidian Canvas の ingest(`*.canvas` 形式)

`raw/_MY_ART/` などの `.canvas` は、1作品・1ラフ単位の制作中資料ボードとして扱う。
`/llm-wiki ingest <path>.canvas` または「Canvas をインジェスト」と依頼されたら、
`skills/canvas-ingest/SKILL.md` を読み、`tools/canvas_ingest.py` を使う。

- これは通常 ingest のサブモードであり、出力先は `wiki/sources/`。
- `raw/` の Canvas と添付画像は read-only。書き換え・削除しない。
- 出力は `wiki/sources/<slug>.md` と `wiki/sources/<slug>.usage.json` の 2 ファイル。
- Markdown は一次観測(source-backed)と LLM 推論(inferred)を分離する。
- Eagle 連携は sha256 完全一致のみ `confirmed`。寸法一致・画素類似は `candidate` に留める。
- 通常は画像 vision を使わず、Canvas JSON / ファイル名 / 配置 / テキスト / Eagle metadata を読む。
- まず `--dry-run` で `confirmed` / `candidate` / `unmatched` 件数を確認し、実行時は
  `--update-index --update-log` で台帳を更新する。

### 講座動画の映像 ingest(video-visual-ingest)

文字起こし済み講座動画の **映像レイヤー**(スライド・作例・live 加筆)を取り込む通常 ingest の
サブモード。正本仕様は `wiki/builds/video-visual-ingest-design.md`。

- 通常の `ingest` では動画を自動検出する。講座・実演・画面操作・スライド・作例比較など、映像が
  文字起こしにない知識を持つ場合は、ユーザーの追加指定なしで映像 ingest まで行う。
- ユーザーが「文章だけ」「映像不要」と指定した場合、同一動画を取り込み済みの場合、または動画候補が
  複数で一意に決められない場合だけ省略・確認する。映像価値が不明なら少数サンプルで判断する。
- 実行モデルは Fable 5 に固定しない。モデル名、確信度、判読可否を記録する。
- 映像観測節は **画面上で確認できた事実のみ**(source-backed)。推論・助言は source に書かない。
- フレームは `wiki/assets/frames/<source-slug>/` に保存され、全パス
  `![[wiki/assets/frames/...]]` で source ページから参照される。`raw/` には書き込まない。
- `tools/video_frames.py --dry-run` で動画の SHA-256、容量、再生時間、抽出予定を確認する。
- 品質ゲート: `tools/video_ingest_gate.py` の `snapshot`(抽出前の同一性記録)と `check --phase complete`
  (完成報告前の来歴・本文非破壊・整合・再確認手続き・台帳検査)は **常時必須**(設計 v2.2)。
  第2読者との不一致は両方許容・記録必須(確定なら corrected / 未確定なら行に要確認表記+marked-uncertain)。
- 等間隔抽出で見つからなかったものを「動画に存在しない」と確定しない。

### LLM 対話ログの ingest(`raw/_llm_logs/`)

ChatGPT 等の外部 LLM との対話ログ(.md)は `raw/_llm_logs/` に置き、通常 ingest で取り込む。

- ログ内の説明・主張は **「外部 LLM の発言」として帰属**し、講座知識・検証済み事実と混ぜない。
- ユーザー自身の発言・採用した理解は user-stated として分離して記録する。
- ユーザーの理解の変遷(言い換え・圧縮・納得の過程)は概念ページの `## 変遷` に残す。

### query (質問が来たとき)

1. `index.md` から関連ページを 3〜10 件特定 → 実ファイルを読む。
2. 関連ページの `現在の統合見解` / `根拠` / `矛盾・未確定` / frontmatter の
   `status`・`confidence`・`evidence_level`・`last_reviewed` を確認する。
3. 既存ページに `status` / `confidence` / `evidence_level` が無い場合は legacy ページとして扱う。
   legacy は「無効」ではないが、強い断言に使う前に `wiki/sources/` または `raw/` へ戻って確認する。
4. `last_reviewed` が無いページは、鮮度(情報が今も有効かどうか)が不明として扱い、強い断言に使う前に
   `wiki/sources/` または `raw/` へ戻って確認する。
5. 必要なら `wiki/sources/` まで戻って、元資料由来の主張か、AI の分析かを確認する。
6. 日本語で出典付き回答(`[[slug]]` を本文に埋める)。`contested` / `uncertain` /
   `ai-hypothesis` を含む場合は断言せず、不確実性を明記する。
7. 価値ある回答は `wiki/analyses/<slug>.md` に file-back し、`index.md` と `log.md`
   を更新。

#### 解釈の壁打ち(ユーザーの解釈・仮説の検証)

ユーザーが自分の解釈・圧縮・仮説を持ち込んだ場合の query 規則:

- wiki の根拠で **支持 / 矛盾 / wiki 未収載** に仕分けて答える。
- wiki に無いことは「wiki 未収載」と明示する。一般知識で補う場合は、補った部分が分かる
  ラベルを付ける(無言で一般論を混ぜない)。
- 講座知識の引用は「講師が該当講座でそう述べた」という発言帰属で書く。
- file-back する analyses ページには、フレーム画像の全パス埋め込み
  (`![[wiki/assets/frames/...]]`)を使ってよい。

### lint (`/llm-wiki lint`)

1. 矛盾 / 切れリンク / 孤立ページ / index 不整合 / 未作成エンティティ / 鮮度切れ /
   `evidence_level`・`last_reviewed` 不足ページ数を洗い出してレポート。
2. 修正はユーザー判断に委ねる(自動で書き換えない)。

### 文字起こし（`/transcript`）

講座動画（Coloso 等）の文字起こし依頼が来たら `/transcript`（`.claude/skills/transcript/SKILL.md`）を使う。
これは ingest / query ではない。指定ページ内の指定動画だけを逐語文字起こしし、指定 Obsidian ページに
追記する（例: `raw/_coloso/2026_05_30_マーセ/coloso_マーセ_08 ….md` の `[[08.mp4]]`。動画は `_attachments/` 配下）。
このタスクに限り、指定 Markdown ページへの末尾追記と同フォルダへの transcript 新規生成を許可する。
`wiki/`、`index.md`、`log.md` は更新しない。

### grill-build(`/grill-build`)

`/grill-build` または `grill-build` と依頼されたら grill-build スキルを使う。
Codex では `~/.codex/skills/grill-build/SKILL.md` を正規入口にし、Claude Code では
`.claude/skills/grill-build/SKILL.md` を正規入口にする。
これは ingest/query ではなく、関連ファイルと現状を先に確認し、必要最小限の質問で曖昧点を詰めて、
実装可能な計画を1つの成果物として出すスキル。自発起動しない。

### brainstorm（会話を切らずに考えを詰める・計画作成まで・明示起動のみ）

## 成果物 Inbox(全ハーネス共通の機械導線)

成果物(新規作成・更新してユーザーに確認してほしいファイル)が完成したら、報告文に加えて必ず
inbox へ機械的に申告する。チャット内リンクの押下可否はハーネス(opencode 等)依存のため、
押せるリンクではなくこの申告が成果物確認の正の経路。

```
python3 "<KBルート>/tools/inbox.py" add "<絶対パス>" --origin <claude-code|codex|kimi|opencode> --task "<依頼の要約>" --note "<見て判断すべき点>"
```

- 申告は窓を開かない(静かに記録されるだけ)。同一パスの未処理分がある場合は弾かれ、既存の短IDが返る。
- ユーザーの入口: Raycast「成果物Inboxを開く」= 未処理ボード(inbox-dashboard.md)を Obsidian でオープン。
  「成果物Inbox処理済み」= 短ID指定で完了化。CLI は `llm-wiki-inbox`(add/list/open/done/board)。
- 正本と経緯は [[deliverable-inbox]]。

## 命名規則

- ファイル名は **kebab-case + `.md`**(ASCII)。日本語タイトルは本文中の見出しで表現。
- リンクは **Obsidian 形式 `[[page-slug]]`**。別名は `[[page-slug|表示名]]`。
- ページ冒頭に YAML frontmatter を必ず付ける。`type` (`source` / `entity` /
  `concept` / `meme` / `build` / `analysis`) と `sources:` (引用ソースの slug 配列) は最低限。
  meme ページは `sources:` の代わりに `clips:`(X クリップ source の slug 配列)を使う。
- AI 精度維持のため、可能なページには以下も付ける:
  - `status`: `active` / `superseded` / `contested` / `uncertain`
  - `confidence`: `high` / `medium` / `low`
  - `evidence_level`: `source-backed` / `user-stated` / `inferred` / `ai-hypothesis`
  - `last_reviewed`: `YYYY-MM-DD`
- source ページで映像 ingest が完了している場合のみ `visual_ingested: YYYY-MM-DD` を付ける
  (途中失敗時は付けない。映像未取り込みページとの機械判別用)。

## ページ構造

### source ページ

`wiki/sources/` は元資料に書かれていることの要約に限定する。推測・比較・ユーザー向け
助言は `analysis` に分離する。

推奨構造:

```
## 要約
## ソース内の主要主張
## 抽出されたエンティティ
## 抽出された概念
## 不確実・要確認
## 関連リンク
```

### entity / concept / meme ページ

複数ソースを統合するページでは、AI が「現行説」と「根拠」と「未確定」を分離して
読める構造を優先する。

推奨構造:

```
## 現在の統合見解
## 根拠
## 矛盾・未確定
## 変遷
## 関連リンク
```

### analysis ページ

`wiki/analyses/` は、質問回答・比較・仮説・ユーザー向け判断の置き場。元資料そのものの
要約ではなく、AI またはユーザーの解釈を含む可能性があるため、`evidence_level` を
必ず明記する。

## ログ規則

すべてのログ行は以下の形式で書く(grep で一覧できるように):

```
## [YYYY-MM-DD] <op> | <タイトル>
```

`<op>` は `init` / `ingest` / `query` / `lint` のいずれか。日付は **絶対表記**。
「先週」「明日」のような相対表記は使わない。

## 言語

Wiki ページ、要約、ログ、frontmatter の値は **すべて日本語** で記述する。元ソースが
英語等であっても要約は日本語化する。タグやファイル名は ASCII でよい。

## 編集の原則

- 1 つのソース取り込みで 10〜15 ページに触れることは普通。**触ったページは必ず
  `log.md` の該当エントリに列挙** してユーザーが追跡できる状態を保つ。
- 誤字・誤変換・リンク切れ・書式整理・明らかな source 要約の精度改善は、通常更新してよい。
- ただし、意味のある主張・解釈・自己理解・方針・評価を変更する場合は、旧主張を
  無言で削除しない。`status: superseded`、`## 変遷`、または `> [!warning] 矛盾あり`
  によって、AI が現行説・旧説・矛盾・不確実性を判別できる形で残す。
- 古い情報を残す目的は「全部を同じ強さで保存すること」ではなく、AI が誤って旧説を
  現行説として採用しないようにすること。
- 不確実な情報は「不確実」と明記。Wiki に書かれていないことを推測で埋めない。
- 既存ページの一括変換は行わない。新規 ingest / query、および今後触る重要ページから
  段階的にこの精度優先スキーマへ寄せる。
- 旧スキーマの既存ページは legacy として扱う。legacy ページは参照してよいが、
  AI 精度優先の回答で強い根拠にする場合は source / raw 確認を行い、触ったタイミングで
  必要な frontmatter や `矛盾・未確定` を追補する。

## Claude Code / Codex / Kimi Code 併用ルール

- Claude Code・Codex・Kimi Code が同時に同一ファイルを編集しない。ingest / query / lint などの
  作業単位で担当を分け、進行中の作業範囲を尊重する。
- 取り込み・質問回答の file-back・lint の結果は、どちらの AI が実行しても必ず
  `log.md` に記録する。
- 他 AI が直近で編集した内容を削除・上書きせず、差分を読んでから追記・更新する。
  主張が衝突する場合は `> [!warning] 矛盾あり` または `## 変遷` で履歴を残す。
- `raw/` は常に read-only とし、正規化・要約・リンク付け・矛盾調整は `wiki/` 側で行う。
- `index.md` と `log.md` を Wiki の監査線として扱い、更新漏れが疑われる場合は
  先に確認してから作業する。

## Obsidian 直開きの共通入口

- LLM が wiki ページをユーザーへ返すときは、Finder で探させず、可能な限り
  `obsidian://open?vault=...&file=...` の **Obsidianで開く** リンクを添える。
- URI の生成は `tools/open_in_obsidian.py <wikiの相対パス> --markdown` を使う。
  空白・日本語は自動で URL エンコードし、保管庫外のパスは拒否する。
